## 0. 一句话方案

把设置 → 模型里那**一个**「派发任务默认模型」升级成**按用途分三套**：`execute`（执行/通用，不传即此项，原配置原样落在这里）、`plan`（方案设计）、`review`（审查/审计）；三套各自存「渠道 + 模型 + Key 归属 + 独立推理强度」，方案/审查**默认跟随执行/通用**、可按需独立配置。`dispatch_task` 新增 `purpose`（用途）与 `thinking`（本次档位覆盖）两个可选参数：**不传按链走、传了以本次为准、值非法就报错且不建半会话**；每套配置取到的值不可用就点名报错，绝不回落到别的用途。

## 2. 现状核对（代码事实）

### 2.1 现在的「三类默认」与档位链

`defaultmodels.go` 文件头已写明体系：**全局默认模型 / 派发任务默认模型 / 待办任务模型**，配置字段在 `config.go`：`DefaultModel ModelRef`、`DispatchModel ModelRef`（`ModelRef` = `provider + providerKey + model + thinking`，`thinking` 空＝不指定）。

现状取值链：

- 手动新建会话 → 全局默认模型（`server.go` `handleCreateSession`：档位 `defaultThinking("global","")`，模型 `applySessionModelDefault`）。
- `dispatch_task` → `t.dispatchModelChoice(model)`：**显式 `model` 参数 > `DispatchModel`（完整才生效）> 跟随主会话（派发者手选 provider/model/Key；派发者没手选→全局默认模型）**；档位 `t.app.defaultThinking("dispatch","")`：**`DispatchModel.Thinking` > `DefaultModel.Thinking` > 空（服务端默认）**，**工具没有档位参数**。
- `dispatch_sub` → `dispatchSubModelChoice`：显式 `model` > 继承派发者；档位固定 `t.sess.Thinking`（`assistant.go`：`Thinking: t.sess.Thinking`，注释「子对话仅继承派发者当前档位，不读取默认体系」）。
- 待办 → `todoModelChain`：待办自选 → 派发任务默认模型 → 全局默认模型；档位 `defaultThinking("todo", own)`：待办自选 > `DispatchModel.Thinking` > `DefaultModel.Thinking` > 空（`todo.go` 派发处同样用它）。
- `dispatch_task` 的**其他可选参数**与人工建会话一一对应：`mode`（工作模式）、`plan_mode`、`attachments`、`permission`、`model`、`workspace`/`remote_workspace`。

关键事实：**档位已经与模型解耦**（`ModelRef.Thinking` 独立字段、`defaultThinking` 只继承档位不换模型），这是本需求「独立推理强度」与「本次 thinking 覆盖」的现成地基。

### 2.2 不静默回落已经是既有口径

`checkModelRef` 是唯一判据：渠道未配置 / 手动停用 / 自动停用 / 模型不在清单 / Key 归属失效 / 无 API Key，一律点名「哪个渠道、哪个模型、什么原因、去哪个设置页改」。`dispatchModelChoice` 里「配置了但不可用」直接报错、不往下试；只有「未配置（空）」才继续下一环。**本方案沿用这条口径，不新造第二套判定**：模型链、档位链、新增的 `thinking` 参数校验都走同一个判断习惯——未配置/未传才继续，写了值就必须能用。

### 2.3 设置页 / API / 消费者现状

- `GET /api/default-models` → `{thinkingLevels, global, dispatch, manager}`；`POST /api/default-models` 收 `{global?, dispatch?}`，**键缺席＝保留、`null`/`{}`＝显式清空**，在配置副本上校验后 `Save` 再换装（`defaultModelsSaveMu` 串行）。
- 设置页 `web/app-settings.js` `loadDefaultModels/renderDefaultModels/saveDefaultModels` + `index.html` 的 `#default-model-block`：两行（全局默认模型 / 派发任务默认模型），每行「模型下拉 + 推理强度下拉 + 生效值灰字」；派发行另有 `follow|custom` 模式下拉；保存是即时接口（不跟卡片底部「保存」）。
- **待办组件 `组件/todo-scheduler/client.js` 直接消费 `GET /api/default-models` 的 `dispatch` 字段**（`d.dispatch.mode/thinking/ref`）来显示待办卡片「当前生效」。→ **`dispatch` 字段的形状不能改**，只能新增字段。
- `web/index.html` 该块注释已写明「dispatch_task 用派发任务默认模型（空渠道/模型＝跟随主会话）」。

### 2.4 其他派发入口的现状（决定「不扩大语义」的边界）

| 入口 | 现状 | 本方案 |
|---|---|---|
| `dispatch_task`（长期助理，顶层） | 用 `dispatchModelChoice` + `defaultThinking("dispatch")` | **唯一**接入用途分派与 `thinking` 覆盖 |
| `dispatch_sub`（任务会话，子对话） | 显式 model > 专家预设 > 继承派发者；档位＝派发者 `Thinking` | 不变 |
| `send_to_session` | 只可能改 permission，**不碰模型/档位** | 不变 |
| 待办派发（`todo.go` → `createSession`） | 三档链 + `defaultThinking("todo")` | 不变（等价于 execute） |
| `run_python` 工具桥 `jx.dispatch`（`bridge.go` `bridgeDispatch`） | 调 `tc.dispatchModelChoice(model)`，**没有 Thinking** | 不变：等价 execute（见 §5.5） |
| 人工建会话 / 分支克隆 | 全局默认（或照抄父会话） | 不变 |

## 3. 设计

### 3.1 用途清单与取值（★ 已拍板：固定三类）

固定三类，**内部 id 与中文标签**：

| id | 中文标签 | 含义（给模型看的判定口径） | 默认 |
|---|---|---|---|
| `execute` | 执行/通用 | 日常执行、通用任务、没特别阶段的活儿；**不传 purpose 即此项** | 配置＝现在的「派发任务默认模型」 |
| `plan` | 方案设计 | 调研规划、出方案/设计文档、先定做法再动手 | 跟随 execute |
| `review` | 审查/审计 | 独立审查、验收、越权/风险审计、对抗性复核 | 跟随 execute |

- ★ id 就用三个小写 ASCII（`plan` / `execute` / `review`），与既有 `mode`（`task/office/coding/beginner-coding/skill-create`）、专家名的做法一致——**工具说明给清单，模型照抄**，不设第二套取值路径。
- ★ 归一规则：`strings.ToLower(strings.TrimSpace())` 后**严格相等**才算数；空串/缺席 → `execute`。
- ★ **不接受中文别名**（"方案"/"审查"）：别名会把 `purpose` 变成自由文本，与「未知用途必须报错」冲突；模型遇到报错会照清单重试（与 `resolveDispatchMode` 同款体验）。

### 3.2 配置数据模型

**原则：新键只新增、不动老键**。`dispatchModel` 原键**原位原义**保留为 `execute` 的配置（老版本 exe 回退仍读得到），新增两个键：

```go
// config.go

// DispatchPurposeCfg 派发用途（方案设计 / 审查·审计）的默认模型与推理强度。
// Mode：""/"follow"＝模型跟随「执行/通用」（推荐默认，也是老配置读出来的零值）；
//       "custom"＝用下面四项；其它值一律视为**脏配置**，读写两处都必须报错，不得降级成 follow。
// Thinking 与 Mode 无关：模型跟随时档位仍可独立设置（空＝沿档位链继承）。
type DispatchPurposeCfg struct {
    Mode string `json:"mode,omitempty"` // ""|follow | custom（其它值＝非法）
    ModelRef                            // provider / providerKey / model / thinking（匿名字段按内层字段平铺）
}

type Config struct {
    // …既有字段…
    DefaultModel ModelRef `json:"defaultModel"`             // 全局默认模型（不变）
    DispatchModel ModelRef `json:"dispatchModel,omitempty"` // 执行/通用（原键原义，不变）
    DispatchPlanModel   DispatchPurposeCfg `json:"dispatchPlanModel,omitempty"`   // 方案设计（新增）
    DispatchReviewModel DispatchPurposeCfg `json:"dispatchReviewModel,omitempty"` // 审查/审计（新增）
    // …既有字段…
}
```

落地后的 `config.json` 片段示例：

```json
{
  "defaultModel": {"provider": "deepseek", "model": "deepseek-v4-pro", "thinking": "high"},
  "dispatchModel": {"provider": "custom-1794646180491", "model": "deepseek-flash", "thinking": "low"},
  "dispatchPlanModel": {"mode": "custom", "provider": "deepseek", "model": "deepseek-v4-pro", "thinking": "xhigh"},
  "dispatchReviewModel": {"thinking": "high"}
}
```

- 上面 `dispatchReviewModel` 只有 `thinking`：**模型跟随执行/通用，档位独立**——「跟随」与「独立推理强度」靠这个形状共存。
- ▶ 用匿名字段嵌入 `ModelRef`：Go 标准库会把内层导出字段按平铺编解码，前端既能像现在一样发扁平对象，也不新增并行类型。若不放心这一行为（要长期维护），退一步用显式四字段复制，语义等价（实施时二选一，推荐嵌入）。
- ▶ 键名用 `dispatchPlanModel` / `dispatchReviewModel`（而非 `dispatchModels: {plan:…}` 这种 map）：三类固定，显式键更利于「未知配置不静默容忍」；将来加第四类属一次有意的配置迁移，而不是悄悄长出未定义用途。

#### mode 值域与校验（★ 已拍板：非法即报错，不降级）

`mode` 只有三个可接受形态，**「空/缺席」与「脏值」必须严格区分**：

| 配置值 | 语义 | 读取（设置页/派发） |
|---|---|---|
| 键缺席 / `""` / `"follow"` | **正常默认**：模型跟随执行/通用 | 正常展示「跟随执行/通用」，生效值算到底 |
| `"custom"` | 独立模型（provider+model 必须齐全） | 正常展示该模型；不全则报「选了自定义但没选全」 |
| 其它任意值（`"Custom"`、`"跟随"`、`"飞"`…） | **脏配置** | **报错**，不当作 follow、不改写配置、不建任务 |

三处行为写死：

1. **保存时**（`POST /api/default-models`）：`mode` 不在上述集合 → 400，文案列合法值 + 指出该填哪个用途的设置位置；不落盘、不改运行中的值。
2. **派发时**：`purposeRef` 读到脏 `mode` → 返回错误，`dispatch_task` 在**建会话之前**失败（不建半会话、不回落 execute、不回落 follow）。文案示例见 §3.7。
3. **设置页读取时**：视图里 `mode` **原样返回脏值**，同时 `ref.error` 写明「用途配置的 mode 非法：…（可选 follow / custom）」；前端下拉遇到不认识的值显示「配置非法：<原值>」并置红（复用现有 `dmSelectRef` 的「已存但不可用」做法），让用户能看见并改回。

> 归一化规则只做大小写/空白处理（`"FOLLOW"`、`" custom "` 这类视为合法并归一），**不做同义猜测**——`"跟随"`、`"跟随主会话"` 一律按脏值报错。

### 3.3 取值链

两条链**互相独立**：模型链决定用哪个渠道/模型/Key，档位链决定 `thinking`；档位链**不因模型是自定义而断**（模型自定义 + 档位留空 = 档位沿链继承，不是「用模型默认」）。

#### 3.3.1 模型链（`dispatch_task` 新建的顶层会话）

| 步 | 取值 | 命中条件 | 来源标注（界面/报错用） |
|---|---|---|---|
| 1 | `model` 参数（本次显式指定） | 参数非空 | 「本次派发的 model 参数」 |
| 2 | 本用途自己的模型配置 | execute：`dispatchModel` 完整；plan/review：`mode=custom` 且完整 | 「执行/通用默认模型」/「方案设计默认模型」/「审查/审计默认模型」 |
| 3 | 跟随执行/通用的配置 | 仅 plan/review 且 `mode` 为空或 `follow`，且 `dispatchModel` 完整 | 「跟随执行/通用」 |
| 4 | 跟随主会话 | 走到 execute 且它不是 custom（空＝跟随主会话） | 「跟随主会话」 |
| 5 | 全局默认模型 | 派发者自己也没手选 | 「跟随全局默认模型」 |
| 6 | 报错 | 全局默认也没设 | `errNoGlobalDefault`（既有文案） |

**链的断点规则（「不静默回落」的唯一判据，必须写死）**：

- 某一环「**没有配置**」（空）→ 继续下一环；
- 某一环「**配置了但不可用**」（渠道没了/停用/自动停用/模型不在清单/Key 归属失效/无密钥/**mode 脏值**）→ **立刻报错**，错误里写清「来自哪个用途的哪一处设置 + 具体原因 + 去哪改」，**不继续往下试、不换渠道、不换用途**；
- 步 1 的显式参数不可用同样立刻报错（既有 `resolveDispatchModelRef` + `checkModelRef`）。

plan/review 的跟随**只跟模型配置**（档位另有链）；但 plan/review 跟随 execute 时，若 execute 是「跟随主会话」，则**一并**跟到主会话（第 4 步）。「跟随」是显式配置的语义，不是回落。

#### 3.3.2 档位链（`thinking`）：本次参数优先

| 步 | 取值 | 说明 |
|---|---|---|
| 1 | **本次 `dispatch_task` 的 `thinking` 参数** | 非空即生效；必须是六档之一（`none/low/medium/high/xhigh/max`，大小写不敏感）。**显式 `none` 是有效取值（关闭思考），不等于未传** |
| 2 | 本用途自己的 `thinking` | 非空即生效（`validateDefaultThinking`） |
| 3 | 执行/通用的 `thinking` | 仅 plan/review 且自己为空 |
| 4 | 全局默认模型的 `thinking` | 非空即生效 |
| 5 | 空 | ＝不指定，服务端默认（`thinkingLevels()` 不含空串，空串一路透传即「不指定」） |

**空串与「未传」的一致规范（全稿统一，不允许各处置不同口径）**：

| 输入 | 语义 |
|---|---|
| 参数缺席（JSON 里没有 `thinking` 键） | 未传 → 沿链（第 2 步起） |
| 显式空串 `thinking: ""` / 纯空白 | **等同未传** → 沿链（空串在本项目里历来就是「不指定」的表示，配置侧 `ModelRef.Thinking` 也是这个口径） |
| `"none"` / `"NONE"` / `" none "` | 有效档位 → 本次用 none，**不沿链**（显式关闭思考） |
| `low/medium/high/xhigh/max`（含大小写/空白变体） | 有效档位 → 本次用它 |
| 其它（`"enabled"`、`"disabled"`、`"ultra"`、`"最高"`…） | **非法 → 派发前拒绝**，列六档与「不传＝沿链」，**不建会话** |

- 六档定义只有一处：`models.go` `thinkingLevels()`；合法性判断复用同一份清单，不新造第二份。
- ★ 本参数**只作用于本次新建的会话**（落在 `sessions.thinking`），不改任何默认设置、不改已有会话、不影响之后的派发（§5.8）。
- ★ 与 `model` 参数同一性质：都是「本次授权覆盖」，都**只在用户明确要求时**才该被长期助理使用（提示词要求见 §3.8）。

#### 3.3.3 优先级总表（自高到低）

**模型**：

1. `dispatch_task` 的 `model` 参数（本次显式指定）
2. 本用途配置（execute=`dispatchModel` / plan / review custom）
3. plan/review → 执行/通用的模型配置
4. 执行/通用为「跟随主会话」→ 派发者会话当前模型（含 Key 归属）
5. 全局默认模型
6. 报错

**推理强度**：

1. `dispatch_task` 的 `thinking` 参数（本次显式指定）
2. 本用途配置的 `thinking`
3. plan/review → 执行/通用的 `thinking`
4. 全局默认模型的 `thinking`
5. 空 = 不指定

> 两条链**只在「同一跳的取值来源」上有关联，彼此不覆盖**：模型自定义不影响档位继承，档位自定义不影响模型选择；本次 `thinking` 覆盖也不会顺带换模型。

### 3.4 `dispatch_task` 参数（★ 两个新参数，▶ 文案）

新增两个可选参数：

```

plan=方案设计/调研规划；execute=执行/通用（不传即此项）；review=审查/审计。

```

- 校验（在建会话之前、与其他参数同样先校验后落库）：

```go
func resolveDispatchPurpose(req string) (string, error) {
    v := strings.ToLower(strings.TrimSpace(req))
    switch v {
    case "":
        return "execute", nil
    case "plan", "execute", "review":
        return v, nil
    }
    return "", fmt.Errorf("purpose=%q 不是可用的派发用途：只能是 plan（方案设计）/ execute（执行/通用，不传即此项）/ review（审查/审计）；用途只决定默认模型与推理强度，与 mode（工作模式）是两回事", req)
}

func resolveDispatchThinking(req string) (string, error) {
    v := strings.ToLower(strings.TrimSpace(req))
    if v == "" {
        return "", nil // 未传/空串：沿链
    }
    if containsStr(thinkingLevels(), v) {
        return v, nil // 六档；none 落到这里，绝不是「未传」
    }
    return "", fmt.Errorf("thinking=%q 不是有效的推理强度：只能是 none/low/medium/high/xhigh/max（none＝关闭思考），或不传（＝按用途配置继承）", req)
}
```

⚠ 实施陷阱（必须照此处理）：**不要直接复用 `normalizeThinkingLevel` 判工具参数**——它会接受老会话库里的 `enabled`/`disabled`（映射为 `""`/`none`），而工具参数只认六档；拿它当参数校验会把 `enabled` 静默变成「未传」，正好违背「非法值必须拒绝」。参数校验只用 `thinkingLevels()` 这份清单（`config.go` 侧的 `validateDefaultThinking` 已是这个口径，可直接复用）。

- **未知用途 → 报错，不建会话、不回落 execute、不猜。**（对应「明确报错不静默回落」；与 `resolveDispatchMode` 既有风格一致，`dispatch_tools_test.go` 的「拒绝先于建会话」模式可直接复用为验收方式。）
- **非法档位 → 报错，不建会话**；`"none"` 必须落到会话上（显式降低思考，不等于沿链）。
- 两个参数都**不参与**其他判定：不改 mode、不自动置 `plan_mode`、不改权限、不改工作区、不改任何配置。
- 派发回报注记（`dispatchTaskNote`）增加两项：`用途：「审查/审计」（review）`、`档位：「本次指定 High」`——**只在非默认时出现**（既有函数就是「只讲与默认不同的点」），避免默认值刷屏。

## 5. 契约（逐条写死，实施与验收都按这个核）

### 5.1 跟随链契约

1. 用途 → 执行/通用 → 主会话 → 全局默认，**每一跳只有「未配置」才继续**；「配置了但不可用」立即报错（§3.3.1）。
2. 跟随是配置语义，不是兜底：plan/review 默认 `mode=follow`，界面上明确显示「跟随执行/通用」，生效值算到底并显示。
3. 跟随只跟**模型配置**；档位另有链（§3.3.2），plan/review 的 `thinking` 留空＝跟执行/通用的档位，而不是「不指定」。

### 5.2 子代理（`dispatch_sub`）契约（★ 不变）

- 模型：显式 `model` 参数 > 专家预设 > 继承派发者（`dispatchSubModelChoice`）；**永不读用途默认**。
- 档位：固定 `t.sess.Thinking`（含为空）；**永不读用途默认/全局默认，也没有 thinking 参数**。
- 既有测试 `TestDispatchSubThinkingInheritance` 必须继续通过；新增反向用例：把 plan/review 配成自定义模型与高档位后，`dispatch_sub` 出来的子对话仍然是派发者的模型与档位。

### 5.3 已有会话与 `send_to_session` 契约（★ 不变）

- 用途配置与本次 `thinking` 覆盖**只在建会话那一刻生效**，不回头改任何已存在会话的 provider/model/key/thinking。
- `send_to_session` 只可能改 permission，不碰模型/档位（既有代码无此路径，本方案不新增参数）。
- 关于「已存在会话的模型」要如实说明一个**既有事实**（不是本方案的改动）：派发时若最终落在「跟随全局默认」而会话上 `provider/model` 为空，运行时仍随全局默认模型解析（`resolveTarget` 的三空分支）。本方案不改变这一点，也不在契约里承诺「钉死」。

### 5.4 待办不受影响契约（★ 不变）

- 待办三档模型：待办自选 → 派发任务默认模型（＝**执行/通用**）→ 全局默认模型（`todoModelChain` 原样复用 `dispatchDefaultRef`）。
- 待办档位：待办自选 > 执行/通用 `thinking` > 全局 `thinking` > 空（`defaultThinking("todo", …)` 不变）。
- 待办**没有**用途概念，也没有本次覆盖参数；`/api/default-models` 的 `dispatch` 字段形状不变 → `组件/todo-scheduler/client.js` 零改动。
- 若某天有人想把待办按用途分派，那是另一个需求（要动待办表单、卡片与调度器），不在本方案内。

### 5.5 其他入口契约（★ 不扩大语义）

| 入口 | 契约 |
|---|---|
| 人工新建会话（HTTP/界面） | 仍只用全局默认模型 + 全局档位（不读用途、不加 thinking 参数） |
| 分支克隆 / 人工子对话 | 仍照抄父会话字段 |
| `run_python` 工具桥 `jx.dispatch` | 仍走 `dispatchModelChoice`（＝**执行/通用**）；不新增 purpose/thinking 参数 |
| 待办调度派发 | ＝执行/通用，档位链不含本次覆盖 |
| 专家预设「模型不可用自动切回全局默认」 | 仍只适用于专家子对话，不扩展到本方案（本方案一律报错） |

### 5.6 旧配置、脏配置与回退契约

| 情形 | 行为 |
|---|---|
| 老 `config.json`（没有两个新键） | 读出来是零值 → `mode=""`＝follow → 与改动前**完全等价**：只有执行/通用一套默认。**不需要迁移、不写迁移任务** |
| 老的 `dispatchModel` | 语义不变，直接就是 execute 的配置（用户已有的选择不会「搬走」或「被重置」） |
| **「空/缺席」与「脏值」的区别** | 空/缺席＝正常默认（follow）；**脏值＝报错**（保存 400、派发不建会话、界面红字），**任何情况下都不降级成 follow、不静默改写配置** |
| 老版 exe 回退运行 | 未知键被忽略：plan/review 会走 `dispatchModel`（＝执行/通用），**不会报错**，只是少了区分；如实告知用户 |
| 老版 exe 保存配置 | 整份重写会**丢掉两个新键**（`Config.Save` 是全量 JSON）→ 再升级回来需在设置页重设方案/审查。**这是已知的回退边界**：文档说明即可，不做自动迁移（迁移会与回退互踩），建议回退前手动备份 `config.json` |
| 用途 `thinking` 非法（配置手改） | 派发时报错（`validateDefaultThinking`），不建会话；界面红字说明 |

### 5.7 未知用途、脏 mode 与不可用契约（★）

- 未知 `purpose` → 工具错误、**不建会话**、不回落 execute；
- 用途 `mode` 脏值 → 派发前报错、**不建会话**、不降级 follow；
- 非法 `thinking` → 派发前报错、**不建会话**、不忽略该参数；
- 用途配置不可用 → 点名「哪个用途、哪一项设置、什么原因、去哪改」后**不建会话**，不换用途/不换渠道/不降级。

### 5.8 本次覆盖（`model` / `thinking`）授权契约（★）

1. **只作用于本次新建的那一个会话**：值落到 `sessions.provider/model/provider_key/thinking` 即止。
2. **不改默认设置**：`DefaultModel/DispatchModel/DispatchPlanModel/DispatchReviewModel` 一个字节都不动；不改全局默认档位。
3. **不改已有会话**：不 PATCH 任何现存会话的模型/档位；后续 `send_to_session` 也不会沿用这次的覆盖值。
4. **不改其他入口**：不影响待办、bridge、`dispatch_sub`、人工建会话的解析路径。
5. **使用门槛在提示词**：只有用户明确要求时才传（§3.8）；产品层面不做额外限制，也不存在「禁止传 thinking」的规则。
