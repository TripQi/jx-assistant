## 1. 目标与信息边界【已确认】

未来会迁入多个嵌入式、上位机等项目。用户首先要看清“各项目还有哪些大目标、分别到哪里了”，需要时再深入其中一个目标，而不是面对按会话、派发次数或改动文件堆出来的流水账。

层次固定为：

```text
项目（一个产品可含硬件、固件、上位机等多个工作区）
└─ 大事件（一个相对独立交付、验收的大目标）
   └─ 推进记录（按事实发生时间排列的关键事实）
      └─ 来源会话 / 消息（同一记录可有多个来源）
```

1. 总览按项目分组，默认展示未结束的大事件：讨论中、处理中、待验收、暂停；已完成、取消放历史筛选，不自动删除。
2. 一个大事件可跨协议、硬件、固件、上位机、联调、评审和返工；这些是同一目标的推进事实，不在总览拆成一堆小事件。
3. 只保留方案确认、重要阶段成果、关键问题、验证结论、阻碍变化、用户验收等关键事实；不记工具调用、读文件、函数修改或测试重跑流水。
4. 严格按“总体 → 单事件推进记录 → 最近相关来源摘要/指定消息 → 必要原文”逐层读取，不默认把所有项目、记录、会话灌入 AI 上下文。
5. 共用宿主项目登记、多工作区绑定和项目生命周期，不强制一个仓库一个项目，不建第二套项目系统。
6. 待办负责提醒、排期、执行；事件负责目标及进展索引，不再造平行待办，也不增加复杂双向同步。
7. 技术知识不塞事件：通用和特殊技术内容均在各自项目知识库完整保存，复用时经判断复制到新项目知识库，不自动同步；本轮不改技能/工作流。
8. 项目隔离、权限交集、归档只读、用户确认删除、追加迁移、并发冲突及来源缺失保护继续保留，按新层次落实。

事件只回答“目标是什么、现在怎样、哪些关键事实支撑判断、去哪里核实”。协议正文、技术方案全文、代码、日志及完整会话仍由原载体保存；记录可写“协议方案已确认”，不能把协议内容粘进来。

## 2. 大事件身份与粒度【已确认】

判断标准：**用户能否对它作一次相对独立的交付/验收决定？** 不能只因换会话、换仓库、换专业阶段或多次返工就新建事件。

| 场景 | 组织方式 |
|---|---|
| “开发设备远程升级功能”，涉及协议、固件、上位机、联调、评审 | 一个大事件，各关键成果记在其推进记录中 |
| 同一缺陷多轮修复、评审退回、用户不满意继续返工 | 同一事件，追加关键事实并修正当前状态 |
| 同一目标派给多个工作会话/子对话 | 沿用同一 `event_id`，关键记录绑定相应来源 |
| 一个会话处理两个可独立验收的功能 | 两个事件，该会话分别支撑有关记录 |
| 原目标外新增能独立交付的需求 | 新建事件 |
| 已验收后出现新的独立复发 | 通常新建；必要时在简短概况中说明旧目标，不新增事件关系图 |
| 纯闲聊、读记录、没有独立交付目标的临时询问 | 不强制登记 |

`project_id`、`event_id`、`record_id` 都是稳定身份，不使用标题、目录名或 `session_id` 代替。创建前在目标项目查当前会话来源、关键词及必要的历史状态，不能只看首页就认定旧目标不存在，也不凭相似标题强制合并。

不做子事件树、可递归阶段、任务依赖图、工时或负责人体系；确有另一个独立交付目标才另建事件。事件中“阶段成果”只是事实，不是带独立状态和排期的子任务。

## 3. 大事件当前概况与状态

### 3.1 当前字段

| 字段 | 含义 | 边界 |
|---|---|---|
| `title` | 用户要交付/验收的大目标 | 不写工具、函数或第几轮派发 |
| `summary` | 目标及当前整体概况 | 随整体结论变化更新，不装时间线 |
| `status` | 当前处境 | 使用下述六状态 |
| `revision`、`updated_at` | 索引修改版本与时间 | 不是代码提交时间或事实发生时间 |
| `record_count`、`session_count` | 推进记录数、来源会话去重数 | 派生计数，不默认展开内容 |

**移除可写的 `latest_progress`、`latest_session_id`、`latest_message_seq`。** 最新关键事实及其来源从推进记录派生，不再维护另一份可能不一致的“最近进展”。总览只取当前概况，不自动拼装完整或最近若干条记录。

### 3.2 六状态【沿用】

| 状态 | 含义 | 默认视图 |
|---|---|---|
| 讨论中 | 目标已登记，方案或边界仍在讨论 | 未结束 |
| 处理中 | 已实际推进，目标尚未交付 | 未结束 |
| 待验收 | 已交付约定成果，等待用户验收 | 未结束 |
| 暂停 | 用户或客观条件使目标暂不推进 | 未结束 |
| 已完成 | 已满足约定完成条件 | 历史 |
| 取消 | 不再继续该目标 | 历史 |

新建未传状态默认“讨论中”；确已开始处理才显式设“处理中”。派发不等于执行，会话空闲、停止、异常退出、某次测试通过或某个待办完成均不自动完成事件。

要求用户验收的目标，执行会话报告完成只能进入待验收；有用户认可依据才进入已完成。无人工验收要求时满足约定验证即可完成，但不能写成“用户已验收”。用户明确原问题未解决，沿用原事件回到处理中；尚未恢复执行时不能声称“正在修复”。

状态按事实由人/助理维护，不引入审批流或自动工作流。暂停、取消、恢复、验收和返工等改变目标判断的事实应留下推进记录，不能只改状态而丢掉原因。

## 4. 关键推进记录与来源

### 4.1 什么值得记【已确认】

每条记录是一项可理解的关键事实，不是本轮做事清单。以下示例均为虚构：

| 应记录 | 不应记录 |
|---|---|
| 升级范围及验收条件已确认 | 已阅读三个源文件、准备检查接口 |
| 固件与上位机已完成主链路联调，尚待断电场景验证 | 改了某函数、调用编译工具、测试重跑一次 |
| 断电恢复验证发现回滚失败，当前交付受阻 | 命令参数、原始堆栈及完整测试日志 |
| 回滚问题验证通过，已提交用户试用 | 一口气复述全部修复尝试 |
| 用户实机验收通过，同意结束目标 | 仅凭会话结束推断验收通过 |

记录可用轻量类型辅助阅读【推荐】：`方案确认 / 阶段成果 / 关键问题 / 验证结论 / 阻碍变化 / 用户验收 / 其他关键事实`。类型不产生子任务，不驱动状态机；“其他”也必须满足关键事实标准。

### 4.2 事实时间与记录时间【推荐】

- `occurred_at`：有依据的事实发生时间，输入带时区，统一规范为 UTC；不得把晚到回报的接收时间伪装为事实发生时间。
- `created_at`、`updated_at`：宿主生成的记录创建、修改时间，调用方不可指定；事件域时间使用固定精度 UTC 表示（推荐固定三位毫秒），不混用偏移或变长小数进行文本排序。
- 无法可靠确定事实时刻时 `occurred_at` 留空，以 `created_at` 排序并明确标注“记录时间，事实时间未明确”，不捏造时间精度。
- 时间线按 `COALESCE(occurred_at, created_at), record_id` 稳定排序，从早到晚展示；首次只取最新一页但页内仍正序，可向前翻页，不先读全量再截取。
- 晚到的旧事实可以补入原时间位置，但不能仅因刚入库就自动覆盖当前概况或状态。更正事实时间可能改变位置，界面提示刷新，不承诺并发期间冻结快照。

这是事实时间线，不是事件旧正文快照：保存“阶段成果、后来发现问题、后续验收”等各自事实；不保存每次编辑前的标题、概况或记录正文。

### 4.3 追加与更正【推荐】

1. 新阶段、新问题、新验证结论或用户反馈，追加一条记录；后来的事实不能覆盖早先确实发生的事实。
2. 错字、事实误录、时间或来源定位错误可带版本原位更正，不另建旧正文历史；真实结论发生变化应追加新事实，不能借“更正”抹掉返工过程。
3. 同一事实的转述、重试保存、同一次测试重复报告不追加重复记录，可给原记录补充确有依据的来源。
4. 状态/整体结论变化时，推荐一次提交“关键事实 + 当前概况/状态变化”，在同一事务完成；仅修正标题错字不制造推进记录。
5. AI 不提供删除能力；误建事件或误录记录可由用户在设置页确认删除，见 §8。删除、更正均不是旧正文恢复系统。

### 4.4 来源关系【已确认，存储细节为推荐】

- 一条记录可绑定多个 sessions，一会话可支撑多条记录；同一会话的不同消息也可分别作为依据。
- 以“记录 → 来源”保存关系，大事件的关联会话由其全部记录来源去重得出，不维护另一套容易漂移的事件会话列表。
- 每个来源至少有 `session_id`，可附 `message_seq`；有消息位置时，宿主必须验证消息属于该会话。新增来源必须存在且满足项目和调用者资格。
- AI 新增关键事实须给出实际依据会话；可以绑定当前会话或执行/评审来源，但不能把未读的转述冒充已核实原文。当前最终答复尚未落库时可只绑会话，不能编造未来 seq。
- 用户设置页直接记录事实允许无会话来源，标注“用户更新”；`origin` 由宿主按入口身份确定，AI 不可指定为用户，不创建假会话。
- 派发只携带项目/事件 ID，不为“绑定新会话”制造一条无意义事实；有成果或其他关键事实时再绑定相应来源。

**来源后来缺失不删除事实。** 会话删除、消息被编辑重发清除、来源归属变化时，保留原关联标识并明确显示状态，不编造替代来源；仅更改其他字段不应因旧来源失效而被锁死。只重新校验本次新增/替换的来源。AI 实质改写事实须给出相应依据，显式移除来源不能把原 AI 事实变成无来源记录；既有来源后来失效与主动删空来源不是一回事，用户原始无来源记录另按其入口身份处理。

宿主的消息 seq 在编辑重发后可能被重新使用，不能仅凭 `(session_id, seq)` 存在就认定仍是原依据。建议在绑定消息时同时保存当时的消息行 ID 及正文摘要哈希（非正文副本）：行 ID 不符标“原消息已移除/替换”，原行正文哈希变化标“来源已修改，需复核”，不能跳到复用 seq 的新消息并伪称原依据仍有效。L1/L2 不为此预读正文；来源列表先给可用元数据判定的缺失/替换状态，正文指纹只在用户选源或 AI 进入 L3 追依据时针对指定消息复核，尚未复核应标明，不把“未检查”说成“原文未变”。

会话整体摘要可能含同会话其他目标的内容，因此优先使用该记录的指定消息；摘要仅用于有需要时定位最近相关背景，不视作该事件的权威状态。来源按 `linked_at DESC, id DESC` 稳定分页只是绑定时间排序，不代表事实新旧；助理应结合所问记录及消息时间选最近相关依据，不能把最后活跃的会话自动当成最新进展来源。

## 5. 字段预算与统一校验【预算已确认】

### 5.1 独立字段额度

| 字段 | 硬上限 | 内容要求 |
|---|---|---|
| `title` | **80 预算单元** | 单行目标短语 |
| `summary` | **240 预算单元** | 一句话当前概况 |
| 单条推进记录 `text` | **240 预算单元** | 一句关键事实，可交代结果及必要限定 |

三个字段独立计数、独立校验，额度不可相互挪用；每条推进记录单独计算。取消此前所有按 Unicode 字符数设置的字段硬限，不再叠加字符数上限。推进记录约有 120 个汉字的容量（标点等仍占预算），**额度是上限，不是写满目标**；只写一句关键事实，不因有余量就塞技术详情或执行流水。

### 5.2 复用现有算法，不新造口径

已核对 `store_projects.go` 的实际函数 `ProjectKnowledgeBudget(content string) int64`，事件字段直接复用此实现，不另造事件专用估算算法：

```text
预算单元 = 2 × CJK 字符数 + ceil(非 CJK 字符数 / 4)
```

- 按 Unicode code point 分类；CJK 严格使用 Go 标准库 Unicode 脚本 `Han / Hiragana / Katakana / Hangul`，包含相应非 BMP 字符，不扩大为所有东亚字符。
- 其他脚本、数字、标点、内部空白、emoji 和组合标记等按非 CJK 计；对**每个字段的完整非 CJK 总数只向上取整一次**，不逐词、逐片段取整，也不把不同字段合并取整。
- 沿用去首尾空白后非空、单行校验，预算计算使用同一待保存字段值；不是 UTF-8 字节数或 UTF-16 code unit 数，也**不等于模型实际 token 数**。
- 后端是预算权威，界面预览复用现有项目预算计算服务/同一函数的结果，不用 JS 字符串长度替代预算，也不另抄一套分类范围；事件保存时仍固定按本节额度校验，不信任客户端传入的用量/上限。只复用计算结果，不照搬知识库“删旧内容/调整额度”的提示或扩容入口，事件超限只精简本次字段。

### 5.3 校验、失败与展示

- 后端统一执行预算、非空、单行及明确格式校验；换行、列表、明显多句/分号拼接流水拒写。允许必要逗号，不开发复杂自然语言解析或额外模型润色。
- 版本号、小数、域名、路径等内部点号不机械当句界；`已完成 v1.2.3 兼容验证，尚待实机验收。`可通过，`已修复。等待验收。`应合成一句。
- 任一字段超预算，**整次拒写**，返回字段名、已用/上限（预算单元）、超出量及“精简为目标短语/一句概况/一句关键事实后重试”等指引；恰好等于上限允许。格式错误同样返回明确修正指引，原值、关系、版本、时间全部保持，绝不静默截断。
- 工具、设置页及未来可能增加的入口共用后端规则；编辑界面按字段显示“已用 / 上限 单元”，写能力说明和错误回执统一使用预算单元，不再以字符计数履行额度契约。不增加长备注、评论、附件正文或隐藏详情字段绕过限制。
- 复用预算算法不等于占用知识库正文额度：事件不扣知识库预算，**也不给整个事件的累计时间线设置总预算**，不删除旧记录腾额度。存储字段预算控制单条内容，查询分页控制单次读取，两者分开；无自动按天/按条数清理。

### 5.4 实施时转成测试的预算样例

复用 `store_projects_test.go` 中既有脚本分类样例（如 `汉あア한` 为 8、`𠀀` 为 2、`abcde` 为 2、`a\u0301😀` 为 1 单元），并新增事件入口的以下边界；这些是将来实现的测试要求，本轮不运行功能测试。

| 输入（仅用于预算边界测试） | 预算与预期 |
|---|---|
| 标题含 40 个 `汉` / 41 个 `汉` | 80 允许 / 82 超限拒写 |
| 概况或单条记录含 120 个 `汉` / 121 个 `汉` | 240 允许 / 242 超限拒写 |
| 标题含 320 个 `a` / 321 个 `a` | 80 允许 / 81 超限拒写，不另加字符数硬限 |
| 概况或单条记录含 960 个 `a` / 961 个 `a` | 240 允许 / 241 超限拒写 |
| `汉abcd` / `汉abcde` | 3 / 4 单元，非 CJK 总数仅取整一次 |
| 标题预算很少但记录达到 241 单元 | 不能借标题余量，整个提交拒写 |
| 多条记录分别符合 240 单元但累计已很大 | 不触发事件总预算，不删旧记录，仅分页读取 |

边界重复串仅验证预算计算，不表示实际标题/事实内容可以用无意义文本通过业务要求；另测混合脚本、非 BMP、组合标记、标点/内部空白、格式及任一字段失败的事务原子性。

## 6. 分层读取与查询契约

### 6.1 读取层次【已确认】

| 层 | 用户问题/操作 | 允许默认返回 | 不应默认读取 |
|---|---|---|---|
| L1 总体 | “各项目还有哪些事？”或“设备甲还有哪些事？” | 跨项目时取分组、计数和概况；只问一项目时直接取该项目概况页 | 推进记录、来源 ID 全表、会话正文、知识正文 |
| L2 单事件 | “远程升级推进到哪了？” | 该事件概况、分页关键记录、少量来源入口 | 所有关联会话摘要/原文 |
| L3 依据 | “这条验证结论依据是什么？” | 选定记录的最近相关来源摘要或指定消息 | 遍历所有 sessions、全历史 |
| L4 追原文 | “当时具体怎么讨论的？” | 必要来源消息的有限窗口，按需续读 | 无条件把整段历史全量塞入上下文 |

用户只问某个明确项目时，可直接调用 `project_events_query(project_id=...)`，**不必先读跨项目事件总览**。项目指代不明确时只查询现有项目登记（如 `project_list`）定位，必要时澄清，不遍历所有项目事件来猜用户所指；此定位不能依赖知识库组件必须开启，应复用宿主登记核心。分层是读取深度边界，不是每次必须走完的固定调用链。

用户在设置页展开项目、时间线或来源，由前后端代码查询、分页和展示，**不需要模型调用**，不触发后台总结；进入模型上下文的只有助理主动查询返回的相应层级。

能力清单只带简短维护/读取指引，事件内容不自动注入所有会话。用户只问总体时，不为了“回答完整”自动深入所有事件或遍历所有分页；有未展示项必须说明数量与可继续查看的入口，不把首页说成全量。单纯查询事件近况无需额外获取项目知识正文，已有知识维护指引应与此衔接；真正开始项目工作或维护知识时再按其规则读取，既有工作会话自身的知识注入机制不在本轮改变。遇工具容量或模型窗口不足须明确指路缩小查询/分页，不静默裁断正文或切换模型、渠道。

### 6.2 项目分组与分页【推荐】

- 项目组来自**全部符合范围且有权访问的已登记项目**，不是从全局最新若干事件反推项目；即使甲项目有很多新进展，也不能挤掉乙项目的分组。
- 项目按 `name, id` 稳定排序；项目页返回总数、已显示数、剩余数及后续游标。未结束事件为 0 的使用中项目也显示计数 0，不制造事件。
- 每组预览最多 3 个未结束大目标及总数，切历史/全部或状态筛选后预览服从同一筛选；项目内独立“展开/加载更多”，事件按 `updated_at DESC, id DESC` 排序，折叠/翻页状态按项目分别维护。
- **AI 与设置页默认页数分开**，以下均为推荐，尚未获用户逐项拍板；分页 limit 的硬上限 40 保留，项目组预览仍最多 3 个目标，不因 limit 增大展开时间线：

  | 查询层 | AI 推荐默认 | 设置页推荐默认 | 单页硬上限 |
  |---|---|---|---|
  | 跨项目总览 | 5 组项目 × 每组最多 3 个目标 | 20 组项目 × 每组最多 3 个目标 | 40 组项目 |
  | 单项目事件列表 | 6 条 | 12 条 | 40 条 |
  | 单事件推进记录 | 最新 5 条，页内事实时间正序 | 最新 20 条，页内事实时间正序 | 40 条 |
  | 单记录来源列表 | 5 条 | 20 条 | 40 条 |

  原先把 20 组项目 × 3 个目标、20 条记录直接作为 AI 默认较宽，故推荐小页减少不必要上下文；这些数量不是实际 token 保证，也不是数据保留数量。设置页可显式传 UI 默认 limit，AI 能力省略 limit 时使用 AI 默认，后端共用权限、筛选与分页规则，不从可伪造的身份参数取得额外授权。

- 不设置跨项目的“总共只给最近 12 个事件”上限；项目页与每项目事件页各有自己的游标、已显示数和剩余入口。跨项目总览仍有界，不一次返回所有项目全部目标。
- 默认 `scope=active`（四个未结束状态），`history` 为已完成/取消，`all` 为全部；显式状态筛选替代 scope 的状态集合。项目归档是另一维度，默认不含归档项目，显式开启可查并标只读。
- 分组显示未结束总数、四状态计数及历史数量。若有状态/关键词筛选，另报匹配数，不能把“匹配 2 条”写成“项目仅有 2 条”。计数只覆盖当前调用者有权访问的范围。
- 名称/路径查项目与标题/概况查事件分开标注；事件关键词只查当前标题、概况，记录关键词在进入单事件后查记录，不为总体查询暗中展开时间线。

### 6.3 建议只读能力

均经现有 `component_call`，不增加新的基础模型工具或另一套 AI HTTP 写通道。

| 能力 | 输入要点 | 返回边界 |
|---|---|---|
| `project_events_overview` | 项目关键词、事件关键词、scope/状态、include_archived、project_limit/project_cursor | 项目分页、计数及每组最多 3 个概况预览、各组事件续读游标；无记录/会话正文 |
| `project_events_query` | 单个 project_id、scope/状态、标题/概况关键词、updated_from/to、可选 session_id、limit/cursor | 单项目大事件概况与计数、revision、归档状态、下一页；session_id 按记录来源关联查找 |
| `project_event_get` | event_id | 单事件当前概况、revision、记录数/来源会话数及项目状态；不自动取时间线 |
| `project_event_records_query` | event_id、记录关键词、occurred_from/to、limit/cursor、向前/向后 | 关键记录分页、每条最多 3 个来源入口及来源数/续读游标；无会话正文 |
| `project_event_sources_query` | record_id、limit/cursor；显式选定 source_id 时可请求单消息指纹复核 | 来源元数据分页、可访问会话标题、消息定位、缺失/替换/归属变化及指纹待复核提示；普通列表不读正文，L3 指纹复核仅定点读一条且不返回正文 |

`assistant` 做单项目列表查询时必须明确 project_id；普通会话可由自身工作区推导，按 event_id/record_id 读取仍须反查所属项目并校验资格。概况/记录/来源使用不同能力，不能一个 get 隐含全量递归展开。

各能力省略条数参数时采用 §6.2 的 **AI 推荐默认**（项目组 5、事件 6、记录最新 5、来源 5），不是设置页的较大默认；显式 limit 仍只允许 1—40。非法或超限 limit 拒绝并指路，不静默修正参数；各页返回匹配总数、已显示/剩余数（有并发变化时标明仅为当前查询时刻计数）、`has_more` 与续读游标，首页不能冒充全量。实际返回不足一页可因到达末尾或工具结果容量，须明确原因和下一页信息，不裁断字段或 JSON。序列化后不能穿过宿主工具结果上限时缩小到完整条目的小页；连一条也装不下则明确报错、指路设置页，不把全局裁切后的坏 JSON 当作成功。

无结果须区分“尚无已登记项目”“当前工作区未绑定”“筛选无匹配事件/记录”，不回退其他项目。时间筛选使用半开区间 `from <= time < to`，非法时间/范围拒绝并指路；日期界面按用户本地时区转换，工具输入带 UTC 或偏移。事件筛选看 `updated_at`，回答“当前最后修改时间在范围内的目标”；记录筛选看已知 `occurred_at`，回答该目标的事实发生时间，未知时间的记录另报数量，不猜归期。二者不可混称“这期间发生过的全部工作”。

关键词是普通文本匹配，参数化并转义 `%`、`_`，不引入向量/全文检索引擎。游标绑定项目/事件、排序与筛选条件，使用时间和 ID 等稳定键，不承诺并发修改下冻结快照；界面可刷新、按 ID 去重，不能因分页就宣称全量一致性快照。

### 6.4 选读来源与现有宿主能力衔接

长期助理可复用 `read_session_summary`，再用 `read_session_messages` 按指定 seq/有限窗口深入。当前五种工作模式及 `aux` 没有前者，但有历史消息工具，可直接读指定消息；不能把“工作会话先调 read_session_summary”写成必经步骤。

`read_session_messages` 当前刻意排除 `kind=summary` 等上下文行，不能把指定该行 seq 当作读取压缩摘要的可用接口。事件组件不另建自动摘要/模型调用系统；无指定消息时按已有入口选读有限历史，不能假装已有一个所有模式都能调的摘要能力。

本组件的项目隔离覆盖索引查询、写入及自动选源；既有全局历史工具的原有访问范围不在本轮重构，不声称它们已全面实施项目 ACL。普通会话仍须只沿自身项目来源按需读取，历史关系不额外授予其他项目正文访问权。

## 7. 写入能力与维护流程

### 7.1 建议写能力

| 能力 | 最小契约 |
|---|---|
| `project_event_create` | project_id、title、summary、可选 status；返回稳定 event_id、revision；讨论中可只登记概况，直接创建为其他状态时须原子附相应有依据的关键事实，不因纯登记动作造过程 |
| `project_event_update` | event_id、expected_revision、变化字段；PATCH 语义，不允许改归项目；实际状态变化须同时附对应关键事实 |
| `project_event_record_add` | event_id、expected_event_revision、幂等键、类型/text/occurred_at/来源；可同时显式 patch 当前概况/状态，不按新记录时间自动推导状态 |
| `project_event_record_update` | record_id、expected_record_revision、expected_event_revision、变化字段、来源 add/remove；仅更正或补充依据，不整体覆盖别的会话新增关系 |

状态变化与事实同事务保存是【推荐】校验，不是审批/流程引擎。大事件标题/概况的小幅纠错可独立保存；所有入口共同执行权限、字段预算/格式、来源和并发校验，写能力说明明确 title 80、summary 240、单条 text 240 预算单元，不能挪用或叠加字符硬限。创建建议用项目内唯一幂等键，记录追加用事件内唯一幂等键；相同键/相同语义载荷重试返回已提交结果，不重复创建；同键不同载荷明确冲突，版本校验不能替代幂等。重试先核验当前权限和项目状态，再判幂等命中；已成功请求不因父 revision 后来变化被误判为新请求或重复追加。

### 7.2 维护时机【已确认】

1. 长期助理安排或工作会话跟进独立交付目标，先在正确项目查已有事件，复用或新建 ID。
2. 派发/续办/评审/返工任务书携带 project_id、event_id，明确同一验收目标；不是每次派发新建事件或推进记录。
3. 发生关键事实才追加记录，整体判断变化才同步更新概况/状态；读文件、改函数、测试重跑等不记。
4. 日常维护只读当前概况/版本及必要的最近记录（推荐先取最新 5 条），核对事实时间、是否重复和当前验收状态，不默认重读整条时间线；确有矛盾或需追依据时才沿记录/来源定点查询及分页深入。晚到旧回报不能因拿到了最新 revision 就冒充最新事实。
5. 冲突重读合并，保存重试复用幂等键；不得强行覆盖、换 ID 重复登记或通过截断内容凑成功。
6. 登记失败如实说明，不能声称已入库；原任务结果与索引维护失败分开汇报，不把已完成工作说成执行失败。
7. 工作会话可维护本项目事件，但项目知识正文仍按现有权限只提修订建议，不因新增事件写权扩大知识写权。

通过工具及简短指引由助理主动维护，不额外后台调用模型，不自动扫描旧会话回填，不宣称保证所有工作必有记录。仅为重复派发而补来源、记录相同事实，不算新的实质进展。

### 7.3 与待办分工【已确认】

“明天提醒联调”“每天执行检查”仍用既有待办；“开发远程升级功能及其关键进展”用事件。一个目标可有多个提醒，也可完全没有待办；两者不是一一对应。

V1 不改待办表、调度器或完成语义；需要关联时，在待办自足描述中携带项目/事件 ID，实际执行产生关键事实后再按本组件规则记录。不因新建事件自动建待办，不因待办完成自动关闭事件，不做强绑定、复杂双向同步或重复排期界面。

## 8. 共享项目、生命周期与权限

### 8.1 复用既有登记【已确认】

复用 `projects`、`project_workspaces`、`projects.go` 与 `store_projects.go` 的项目身份、路径规范化和最长目录边界匹配；本地/远程命名空间分离，同一规范绑定唯一，离线目录保留，符号链接/junction 不自动猜归属。一个产品可显式绑定硬件、固件、上位机等多个工作区，不从 Git 仓库数量推导项目。

新建/改名/绑定、归档、恢复、永久删除项目仅由用户在设置页执行。未登记时引导既有管理入口，任务可继续，但不擅自建项目、写到其他项目或创建收件箱。

目录重绑不搬旧事件，事件 project_id 不变；会话后续资格按当前实际工作区解析，更具体的归档绑定不回退外层项目。历史来源关系保留，但不意味着重绑后该会话的新内容仍属于旧项目。

### 8.2 生命周期与删除【沿用，适配记录层】

- 使用中项目正常查写；归档项目只读可查，禁止新增/更正记录或维护来源，不停止运行任务。恢复或确认永久删除仍由用户管理入口执行。
- 两组件独立开关，关闭知识库不影响事件，关闭事件不影响知识库；关闭任一组件均不删共享登记或已有内容。事件使用自己的生效开关，不能依赖知识库能力恰好开启。
- 单个事件永久删除仅用户设置页确认，事务内删事件、推进记录、来源关系；删单条误录推进记录也须用户明确确认，清理其来源并刷新派生计数，不删其他记录。
- 永久删除项目由既有用户入口确认，级联清理绑定、知识、事件、记录及来源；不删除 sessions、消息、代码、附件或工作区文件。
- 归档项目的只读限制不妨碍用户恢复或经确认的永久删除。删除对话需说明范围、不可由组件恢复，并让用户检查当前概况是否需要调整，不能静默重写其结论。
- AI 不暴露项目结构管理、事件/记录删除、自动合并或正文恢复能力；重复目标由用户确认整理，不做自动合并引擎。

### 8.3 角色与权限交集【沿用】

| 调用者 | 查询 | 新建/更新事件、记录、来源 |
|---|---|---|
| `assistant` 长期助理 | 跨已登记项目，按需含归档 | 使用中项目，跨项目维护 |
| `task / office / coding / beginner-coding / skill-create` | 自身实际工作区绑定项目 | 自身绑定且使用中的项目 |
| `aux` | 自身绑定项目，只读 | 不允许 |
| 用户设置页 | 全部项目 | 使用中项目可编辑；归档只读，管理入口可恢复/确认删除 |

后端校验**合法当前会话、角色、实际权限档、计划模式、事件组件生效开关、项目归属及项目状态的交集**；read-only/计划模式拒写，workspace-write/full 也不能越过角色和项目边界，子会话不无条件继承父项目。

普通会话不得借伪造 project_id、event_id、record_id、session_id 或游标跨项目，其新增来源只接受当前可确认归属同项目的会话。长期助理可额外关联跨项目协调用的 assistant 会话，但应携带明确目标标识或有可核验的派发/回报关系，不能把任意其他项目会话当来源。服务端验证存在性、调用资格、来源角色及可验证关系，助理负责业务相关性判断，不假装能用函数证明语义相关；设置页用户须明确选择目标项目与来源。

既有历史来源若被删、失去可确认归属或目录已重绑，关系仍留在原项目，普通会话不自动展开跨项目来源正文或泄露其新标题/摘要，提示由长期助理核实。保留索引不是新增阅读授权；本次不涉及来源的修改仍可继续。

AI 全部走 `component_call`，写能力在 manifest 标记 `writes:true`，覆盖 assistant 与五种工作模式但不含 aux；查询另含 aux。设置页区分用户身份，沿用现有项目设置入口拒绝 AI 调用的约定，复用业务校验，不能作为 AI 绕过角色的旁路。

## 9. SQLite 表、事务与迁移【名称及细节为推荐】

### 9.1 单库及关系

继续使用当前实例既有 `jx.db`、Store 连接和事务，分表不分库；不同实例/dataDir 不自动共享。不新建项目域数据库、全文副本或事件历史正文表。

| 建议表 | 主要字段 |
|---|---|
| `project_events` | id, project_id, title, summary, status, revision, created_at, updated_at, create_key/create_digest（可选幂等） |
| `project_event_records` | id, event_id, kind, text, occurred_at（可空）, origin（AI/用户）, revision, created_at, updated_at, client_key, request_digest |
| `project_event_sources` | id, record_id, session_id, message_id/message_seq/message_digest（可空）, source_key, linked_at |

- 项目 → 事件 → 记录 → 来源均设所属外键及向下删除级联；project_id、event_id、记录归属不可通过更新接口搬迁。
- **来源不设置指向 sessions/messages 的外键**：既不能级联清理来源，也不能以 RESTRICT 阻止用户删除来源会话；保留失效 ID，新关联入口验证存在性，查询时再报告可用性，不持久复制会话正文。
- `UNIQUE(event_id, client_key)` 防重复追加；请求摘要用于识别同一键不同语义载荷，不保存旧正文。事件创建如采用幂等键，在项目内唯一。
- 来源唯一键推荐 `(record_id, session_id, source_key)`，source_key 非空，区分“会话级”与“消息行 ID”，避免 SQLite NULL 唯一约束导致重复；同一来源重复添加是 no-op。
- 会话去重数由来源推导，推荐索引：事件 `(project_id, status, updated_at, id)`；记录 `(event_id, COALESCE(occurred_at, created_at), id)`；来源 `(record_id, linked_at, id)` 及 `(session_id, record_id)`。实际表达式索引按查询计划核对，不预建大型统计系统。

### 9.2 原子性与并发

- 写入采用 PATCH 与 `expected_revision`。所有子记录/来源变化同时递增父事件 revision；记录自身正文/时间/来源变更再递增记录 revision。严格串行版本能接受偶发冲突，不上复杂合并引擎。
- 事实追加、来源 add/remove、显式概况/状态变更及版本时间更新同事务；任一校验或落库失败全部回滚。已有来源列表不能整体覆盖，重复来源不刷新版本。
- 仅读取、展开、相同值保存、相同来源重复添加和幂等重试均不刷新排序；确有任何有效内容/关系变化才更新相应 revision、updated_at。
- 修订号只用于并发控制，不代表历史快照。它不能判断旧回报是否语义过时，必须结合事实时间与最近状态人工/助理判断。
- 写事务内重新读取调用会话的当前 mode、permission、plan_mode、workspace/remote 及项目状态/绑定，防授权或归属变化；不能拿旧运行指针作授权。组件开关按当前会话生效值核对。
- Store 为单连接并有写锁，事务内校验使用同一 tx 的查询辅助函数；不得持锁再调用 `Store.Get`、会重新取 Store 的项目解析等，避免重入死锁。授权校验复用公共权限门和共享解析核心，不复制一套权限引擎。
- 成功写入只返回提交结果中的 ID、revision、时间、saved/created 标志等小回执，不再读全部记录/来源后才宣布成功，避免“已落库却因回执过大报失败”。

### 9.3 追加迁移及旧数据

结构升级只在实施时向 `storeMigrations` 末尾追加，经 `schema_migration` 与 checksum 记账，不改已应用迁移，不混用程序目录资源迁移账本。

核对基线中 `0021_project_knowledge` 已建共享项目三表，`0022_usage_out_ms` 已在后；事件迁移编号以实施时最新末尾为准，不能回头改 0021 加事件表。当前源码没有已实现的旧事件表，不需要把旧设计里的 latest 字段当作真实数据迁移；也不因方案升级自动读旧会话补时间线。

若实施时确有其他分支已产生旧事件数据，先核实实际 schema 和来源，经追加迁移保留可确认的当前信息；无法恢复的历史进展明确缺失，不从当前概况臆造过程，不自动清空或覆盖真实数据。

## 12. 验收场景

1. **跨项目可见性**：甲项目有上百个新事件，乙项目仍有独立分组和正确计数；项目分页与项目内分页独立，0 项也明确，不用全局最近 12 条裁掉项目。
2. **粒度**：“开发远程升级功能”跨协议、固件、上位机、联调和多轮返工仍为一事件；各阶段不变成子事件，同会话可支撑多条记录/多个目标。
3. **事实而非流水**：读文件、函数改动和重复测试不生记录；方案确认、阶段成果、关键问题、验证、阻碍变化和验收形成短时间线，技术正文不入事件。
4. **时间与晚到回报**：旧事实晚到能补入原时间位置，未知时刻明确标注；不得自动把旧回报改成当前状态，事实时间与修改时间筛选不混用。
5. **状态**：默认讨论中，派发不自动处理中/完成；需用户验收则先待验收，返工沿用 ID；默认四个未结束状态，完成/取消在历史，暂停仍可见。
6. **L1/L2/L3/L4**：明确单项目可直查、不先读跨项目事件总览，指代不明仅定位登记/必要澄清；总体不读记录/会话，单事件才分页读记录，日常维护不重读整条时间线，追依据定点选摘要/消息，必要再追原文；设置页展开不产生模型调用。
7. **多对多及来源身份**：一记录多会话、一会话多记录，重复关系不增计数；消息 seq 属于对应会话，消息行被替换或原正文被改可识别，不能误跳到复用 seq 的新内容。
8. **来源缺失与重绑**：来源删除、消息清除、项目重绑保留旧事实和标识；普通会话不从历史关系得到其他项目新正文/标题，其他字段仍可改。
9. **隔离与开关**：一个产品多工作区共享，跨项目不可伪造 ID/游标读取；归属按目标工作区，知识组件关闭不影响事件；未登记不回退其他项目。
10. **权限交集**：assistant 跨项目、五种工作模式仅本项目、aux 只读；read-only/计划模式/缺合法上下文拒写，full 也不能跨角色边界；设置页不是 AI 旁路。
11. **并发与幂等**：过期 revision 拒绝且保留草稿，同事务失败不留半条事实/来源；重试无重复，关系增量合并，无变化不刷新；事务授权复核不重入单连接死锁。
12. **字段预算与分页**：标题 80、概况 240、每条记录 240 单元独立校验，直接复用 `ProjectKnowledgeBudget`；覆盖 §5.4 的恰好上限/超限、四脚本与非 BMP、非 CJK 整字段一次取整及不能挪用额度，不加字符硬限。任一字段超限整次拒写、提示已用/上限及精简指引，失败原值/关系/版本/时间不变；不设时间线累计总预算、不删旧记录腾额度。工具与设置页一致，查询分页有计数/余量/续读且结构完整；AI 推荐默认 5 组 × 3 目标、事件 6、记录最新 5、来源 5 与 UI 默认分开，显式条数上限仍为 40。
13. **归档与删除**：归档可查不可写，恢复后可写；用户确认删除按层清理索引，不删除 sessions/消息/代码/文件，组件关闭不丢数据，无旧正文恢复入口。
14. **单库迁移**：只追加到届时迁移末尾，不改 0021/0022；不凭旧设计臆造存量表或历史事实，不访问真实运行库做验证。
15. **待办/知识边界**：提醒与执行仍用待办，其完成不自动完成事件；技术知识不被事件吞并，技能/工作流不改，不增平行待办或复杂同步。
