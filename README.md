## 万物归一，一应万物

我们的核心理念，说来有点中二：**万物归一，一应万物。**

**万物归一**——你的一切操作都没必要搞得很复杂，都应该在同一个入口里完成。所以有了「长期助理」：编程、办公、查资料、派任务，你只跟一个人讲就够了。我们很不喜欢那种「看起来只开了一个终端，背后却跑着一堆浏览器、编辑器和各种进程」的方案。在编程这件事上，我们的目标是：只要这一个工具，就能完成所有的编程工作。

**一应万物**——有了服务端，团队协作的事情就该一处建设、全员共享。一个人的 AI 跑通了一件难事，整个企业的 AI 就都应该会做这件事；最好的技能、小程序、最新的更新，一处发布，所有人同步受益，不必各处重复造轮子。

## 设计理念

这是一个**企业级方案**，但我们坚持让它为每一个人设计。特别在意人性化：按钮怎么摆、功能叫什么名字，都为了让人一看就懂——不懂技术的同事也应该能轻松上手。

我们**非常相信 AI**。AI 就像一个人：要做什么、要用什么工具，应该由它自己判断，我们只负责提供工具和护栏。所以技能、组件、MCP 连接器在这里**全部自动加载**，AI 自己决定什么时候用什么。WrokBuddy（沃克巴迪）就不是这样：技能和连接器要人手动开启，没开就不会用，开了又强制干扰模型，两头难受——模型的智商经常因此显得很低，想做件事又因为缺技能做不了。

用 **Go** 写，能多轻就多轻：安装简单、使用简单、依赖能减就减。我们特地没有用 Electron 那样的技术栈——明明每台电脑都已经有浏览器、有 WebView 了，没必要再拖一个进来。保密前提下，语音输入、语音朗读都可以完全在本地完成。

## 开发历程

首先要**感谢 DSH（DeepSeek Harness）**——它是一个很好的老师。很多东西，确实是我们在它那里体验过之后才知道哪里不好，这本身对我们意义重大。我们也确实从它那里获得了灵感，一些实现起到了参考作用：比如 Office 技能、发版与更新机制、还有「模式」这个概念。所以我们把做出来的好东西开源出来，希望社区也能从我们这里得到一些启发。

最初我们给 pi 做适配、在它基础上开发，但社区组件太杂，本体又太少，各组件之间很难组合。DSH 推出后，我们从它的第 1 个版本就开始基于它做定制——那时候 DSH 还缺很多东西：我们自己造过沙箱、造过浏览器，有些官方后来补上了，有些我们做得不错但前人没做过。基于 DSH 的定制版第 2 个版本（V2）也开源在 GitHub（`DSH-坚祥-V2`），基于 DSH 开发的同学应该能从里面找到不少灵感。

关于「模式」多说一句：DSH 的模式分得不清不楚，很难搞清楚什么时候该用什么——模式是有价值的，但结果大家基本都只用标准模式。**我们的模式是针对场景设计的**：先考虑哪种场景该配哪种模式，再考虑别的。工作区其实除了编程模式以外，在其他功能里根本就不关键。

真正让我们下决心重写的是：给 DSH 开发插件实在太痛苦了——插件机制和文档机制都不合理，而本体不稳定又直接导致插件难以开发。于是我们干脆用 Go 从头写了一个自己的版本。9 月中旬动工，只花了几天时间，使用体验就已经超过了 DSH——当然，bug 也不少。整个 10 月，我们一边做功能，一边主要在修 bug。

我们本来打算 10 月 1 号开源，但从更新记录也能看出来，一直没抽出时间整理。直到看到 DSH 官方做了 super agent，觉得终于有人往这个方向想了——功能实现上我们目前做得非常优秀，那就拿出来，行业一起共同进步。

（说实话，我们其实一直处于开源状态：代码仓库从 10 月 1 号起就是公开的，最近因为里面混入了一些客户信息才转为私有，整理干净历史之后，有了现在这个干净的版本。）

## 功能特色与先进性

### 长期助理：不需要专家团

传统做法是预设一组「专家」角色，但预设总是有限的。jx-assistant 的思路简单得多：**你只管跟数字助理聊天，需要往下派活时，它自动为每个任务写出最合适的提示词**——无非就是它往下发命令时给 AI 写什么提示词的问题，反正用的都是同样的模型。你也可以在聊天里告诉它「这类任务用某个模型更合适」，它会记住。

效果比一切专家团都好。主对话与子任务、数字助理与每个工作任务之间的沟通机制，简单明了，但方案是先进的，效果也非常好。你不再需要预设任何专家——数字助理会替你考虑。

### 告别任务面板

编程场景里，工作任务的排布变得非常简单：**不需要任务面板、看板、定时任务**。我有时候一次会讲出 8 条甚至十几条要做的修改，其中有些还不能同时改——以前只能人盯着，或者设定时任务几点钟做哪个。现在你只管把这些需求一次性讲给数字助理，它像一个人一样盯着整个项目：逐个派发、验证结果，确认没问题再派发下一批。

边界也很清楚：特别需要人机交互、需要你亲自验收的工作（更多是你在跟 AI 沟通），建议直接开新对话自己处理；各种功能性、后台性的任务，交给数字助理效果更好。

### 上下文压缩：无感、便宜、风格不变

压缩算法的目标就三件事：**尽量高的缓存命中率、尽量低的成本、尽量保住压缩前的思考与话语风格**。默认走**模型摘要**：把较早的历史整理成一份结构化摘要，最近的对话与思考过程保持原文——所以压缩之后，它跟你的对话几乎是无感的。想更省钱、更快的话，把规则阈值调低就会改走**零成本规则折叠**（折叠保留用户输入与结论原文），那种压缩快到经常感知不到发生过压缩。再也不用忍受其他软件里那个烦人的压缩提示了。

一个我们认真做过的取舍：**读文件这类工具的内容，照常压缩，不做豁免**。因为文件内容会过期，专门做一套新鲜度判断本身很复杂，而且就算在一个对话里判断得了，跨对话、跨软件也无从判断。压缩发生时其实已经做了很多事了，那些旧文件内容作用不大——最核心的内容都在最近的思考里；真要重新了解项目，让 AI 重新去读、去调研就好。为了省一点调研而保留过期记忆，反而容易调研不足、做错方向。

这个方法并不完美（我自己都还不满意），但已经足够好。

### 组件机制：完全热更新

我们自己的扩展不叫插件，叫**组件**——「插件」这个名字特意让出来给兼容生态（DSH / Clocode 插件）。组件完全热更新：通过桥接层跟主程序连接，可以注册工具、在设置页加配置、改前端、改后端，随时开关、即时生效，不用重启。少数内置组件与主程序耦合较深（多方考虑），但也做成了组件形式——主要就是为了不想要的时候可以关掉。

设想中的插件兼容层更有意思：安装 DSH 插件时由 AI 现场写一个转译桥，每个插件进来都自动生成兼容层——只消耗一点 AI 算力。这套机制目前还没做好（纯粹是时间精力不够），**很欢迎社区一起出力**。不过做不完美关系也不大：搬插件时让 AI 把核心逻辑重写一遍就好，素材资源照搬、换个语言重新实现，对 AI 来说非常容易——尤其对开源项目来说。

### 手机连接器：远程体验跟本地一样好

我们做过 Go 原生手机版（Termux，能跑真实任务），但后来放弃了——在手机上跑 AI 助理本体，价值不大。真正有价值的是**手机远程查看器**：电脑开着的情况下，用手机很方便地指挥电脑。远程连接用起来跟本地几乎一致（除浏览器本地客户端的硬性限制外），不管是用手机浏览器远程查看，还是用我们的手机连接器，体验都非常优秀。敢说这是目前所有智能体里手机端体验最好的。

### 语音输入：识别不完美，配合是顶级的

为「语音编程」服务的语音输入。敢说比微信的语音输入好用——微信语音输入句子一长，后面就断字、丢尾巴；我们不会。阿里 Qoder 那样的产品会在发送前做一遍「润色」，但润色经常丢失用户本意，润色之后还不如原始消息——语音里的「嗯、啊、呃」这些语气词其实是有信息量的。我们的识别不算最完美，但**跟模型配合得非常好**：模型知道这是语音输入，不会去做无谓的纠错。综合下来，这是软件里非常好用的语音输入，你几乎不需要修正。

语音组件还会继续更新，之后会换成语音输入法同款模式，体验再上一档。

### 权限与安全：让标准权限真正可用

很多软件的权限管理根本不合理：只能用完全访问，不用完全访问很多任务就没法跑。WrokBuddy 宣传什么安全都是空话——所有人都只能开着完全访问才用得起它的软件，那根本谈不上安全，也谈不上权限管理。

DSH 这一点做得比较好：它有沙箱机制，标准工作区能解决掉大部分任务。**我们在此之上更进一步：在两档之间加了能力开关。** 有时候你只是想让 AI 操作一下浏览器，没必要非开完全访问——那会多出一大堆风险。有了能力开关，对 AI 的控制更细、更合理、更安全。

权限管理的核心目的是**防止 AI 犯错把电脑搞坏**。权限区分只有「标准权限本身能做得合理」才有价值——不然一切的权限区分，最后大家都是开完全访问。在我们用过的软件里，只有 jx-assistant 是真的可以长期用「工作区内修改」这一档来做开发、做工作的。为此我们做了很多小优化，就不一一介绍了。

安全思路上我们也转过弯：以前做过各种命令对抗、AI 对抗的加固，后来想明白了——你做得再严，别人换一个工具、换一个 agent 就绕过去了，对抗式强调安全没有价值；恶意要破坏计算机、破坏团队，永远都拦得住吗？永远拦不住，特意去拦没有意义。**安全真正该保证的是：执行时避免 AI「不小心」犯错导致的安全问题。** 命令自动转义、危险命令自动拦截、避免 AI 犯错，这些方面我们做得很不错。而且这不是空谈——**实测在办公、编程尤其是测试环节，减少犯错直接带来了 token 节约：消耗常常只有其他智能体的 50%~80%，最好的时候能省一半。**

另外，企业场景下我们的安全机制做在**服务端**而不是客户端——配合企业服务端使用，才是完整的安全方案。

### run_python：把运行时用到位

Python 已经是这个软件的必要运行时（随包附送），那就应该把它利用好，而不是让 AI 每次都「写一个 .py 脚本 → 命令行执行 → 再读输出」绕一圈。我们做了 **run_python**：AI 直接把代码写进去，写的内容就是脚本，执行完直接返回结果——跟写脚本一模一样的模式，但省掉全部中间环节。顺带绕开了 Windows 中文字符、引号转义等一整类问题，大幅提高任务效率，也节约 token。

### 为中文 Windows 而生

目前中文 Windows 环境里，居然没有一个做得好的强力 agent——我们敢说，中文 Windows 环境下目前最强的 agent 就在这里。做的事本质上不复杂：运行命令时强制注入格式要求（编码、字体），告诉模型想用别的字体要自己设置，默认一切都是支持中文的；再加上 run_python 直接执行，彻底避免中文与引号转义的坑。都是些「没人愿意认真做」的脏活，但正是这些细节决定了 agent 在中文 Windows 上能不能干活。

### 为办公而生

办公场景下，整套**文件机制**非常合理：文件修改自动留快照、可回退，备份机制完整——AI 改坏了文件，随时可以恢复。效率上比其他办公 AI 强，token 消耗也更低（见「权限与安全」一节的实测数据）。

权限上也为办公做了专门设计：**标准模式下就能做好 Office 工作**。这里有个有意思的暗桩设计——标准模式的 AI 其实被允许调用 COM 接口，但我们不告知它。一般情况下它不知道怎么用、也不会去用；只有当它真正去做 Office 任务、读了 office 技能文档，才会发现系统给它预留了这个口子——原来在标准模式下就能把 Office 做好。权限该收紧的收紧，口子该留的悄悄留。

### 为编程而生

- **文件查看**：专门为「看文本文件 + 看最近改了什么」设计。AI 编程时，人最常看的就是最近的改动，这个工具就是为这种工作方式准备的。
- **Git 面板**：太复杂的 Git 工作交给 AI 处理；简单操作和图形化查看留给人。做得还不错，但不完美，欢迎一起改进。
- **内置 MD 查看器 + 浏览器**：安装时会带上一个独立的 MD 查看器；浏览器用来看 HTML / MD 这类编程相关文件，效果比没装之前好很多——拿代码编辑器看 Markdown 的体验，你懂的。
- **该系统管的交给系统**：Word 文档之类的东西，就该由系统程序打开。很多工具喜欢把一切塞进右侧栏内嵌查看，那经常是人工操作的阻碍，而不是加成。

### 技能创建模式

技能创建器与「创建技能」这整套模式本身就很有意思：AI 在会话中把跑通的工作流沉淀成一个技能（`SKILL.md` 说明 + manifest + 脚本），下次遇到同类任务直接复用——今天给客户做的点检流程，明天就是一条「跑设备点检」的指令。技能可以自己长出来，而不是等人来开发。

### 新手编程模式

为了让每一个人都能上手而做的模式——不懂编程的人，也能让 AI 替自己写程序。模式是针对场景设计的，新手编程就是其中之一：把门槛降到「说清楚你想要什么」。

### 文档机制：为 AI 时代而生的文档机制

我们的设想里，只应该有一个比较短的文档，讲核心的开发理念与开发原则——也就是仓库里的 [AGENT.md](AGENT.md)。这个文档后来变得很长，没关系，模型反正也只看开头。我们不限制 AI 写文档，但不要求它写；AI 想把东西记录在哪里，都无所谓。同样，我们要求 AI 看的文档也只有这一个——最基础、最简单的开发规范。

我们特别讨厌写一个又一个独立的文档。像 TypeScript 那样把代码和注释结合起来自动生成文档，那是过去**给人看**的东西：人读代码困难、费时间，人读文档轻松，有了文档就能去搜索、去翻阅。但对 AI 来说，看文档（尤其是实现逻辑类的）价值远远不如直接看代码——反正都是文字，代码还更容易理解、更准确。

那还值得用代码以外的东西记录什么？**设计意图**。设计人员的设计意图，应该直接注释在代码里。

这套机制大幅避免了我们曾经给 DSH 做开发时的状态：一边翻文档一边改代码，浪费时间，还容易出错。

其实我们软件里设计的一切，几乎都是面向未来的：文档机制面向 AI，工具与组件面向未来，轻量化架构、长期助理、压缩机制都是。这个软件很核心的一点，是开发的时候从思想上就没有历史包袱——不强求兼容以前的开发习惯、使用习惯，而是用新的、更好的东西去替代。

## 企业版

企业版与社区版客户端是同一个东西——区别在于**服务端没有开源**（有安全考虑，也是商业机密）。安全机制做在服务端，这也是它的一部分。有了企业服务端：

- **一个 AI 的成功，成为所有 AI 的能力**：任何一个人让 AI 跑通了一件难事，全企业的 AI 都能共同成长。
- **企业小程序平台**：公司服务器统一提供，任何人、几个团队之间的协作都变简单——请假、报价、点检，一个小程序搞定，全员共享。
- **企业技能包 / 工作流**：一处发布，全员最新。

社区版里小程序平台与企业技能包 / 工作流暂时使用不了，主要因为需要有人提供服务器。

## 未来计划

- **AI 之间的沟通工具**：让同一团队里每个人、每个人的长期助理能够直接对话（多人 + 多 AI）。这件事权限非常敏感——理论上一个人可能通过沟通工具指挥别人的电脑做危险的事，权限怎么收紧、对话怎么设计，我们还在思考，但未来确实有必要做。

## 🚀 快速开始

```sh
git clone https://github.com/<你的用户名>/jx-assistant.git
cd jx-assistant
go build -o jx-assistant.exe .

./jx-assistant.exe            # 首次启动自动生成 config.json 并打开浏览器
./jx-assistant.exe -desktop   # 桌面模式：WebView2 原生窗口
./jx-assistant.exe -webdir web -port 9000   # 开发模式：前端改完刷新即生效
```

首次使用：打开就是空的（出厂不预置任何模型通道），两条路二选一——
「公司接入向导」一键接入公司通道；或左下角「设置 · 模型」→ 添加提供方，填任意
OpenAI 兼容 API 的地址 + Key。没有 Key？地址填 `mock`，离线跑通全部交互。
