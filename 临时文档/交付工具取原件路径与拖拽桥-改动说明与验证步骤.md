# 交付工具取原件路径 + 拖拽原件路径桥（改动说明与验证步骤）

2026-10-16 · 会话「我们的交付工具是稍微有点小问题…」

## 一、问题（读码 + 真机实测确认）

1. `deliver.go` 的交付目标**本来就是**上传记录里的原件路径所在目录
   （`filepath.Dir(up.OrigPath)`），目标处同名文件先快照到
   `.jxai/delivery-backups/<会话>/` 再替换。工具没问题，问题在「谁登记了原件路径」。
2. 只有一条上传路会登记：桌面壳「＋→文件上传」（`/api/pick-file` 原生选择框 →
   `POST /api/sessions/{id}/upload` JSON `{path}` → `registerUploadPath`）。
3. **从桌面把文件拖进输入框**走的是另一条：`app-chat.js` 的 drop → `stageFiles()`
   → 发送时 multipart 上传，只写字节进工作区、**不登记原件路径**（浏览器、手机、
   粘贴上传同理）。模型要用交付工具时只能得到「本会话没有可解析的上传记录」。
4. 根因：WebView2（Chromium）不把文件绝对路径交给页面。真机探针（独立 WebView2
   窗口，`.jxai/tmp/dropspike`）实测拖入一个文件后页面侧拿到的是：
   `hasPathProp:false`、`pathValue:""`、`uriList:""`、`textPlain:""`、
   `entryFullPath:"/main.go"`（只有文件名）。

## 二、改动

### 1. 宿主侧拖拽路径桥（新增 `dropbridge_windows.go`）

页面把拖入的 File 对象经 `chrome.webview.postMessageWithAdditionalObjects(msg, files)`
交给宿主，宿主从 `WebMessageReceived` 的 `AdditionalObjects` 里读
`ICoreWebView2File.Path`（SDK 原文：*obtain the path of a File dropped on WebView2*），
再经 `w.Dispatch` → `w.Eval` 回调页面 `JX.onNativeDrop({batch,paths})`。

- IID / vtable 槽位取自 WebView2 SDK（NuGet `Microsoft.Web.WebView2` 的
  `WebView2.idl`）：`…EventArgs2` slot6 `get_AdditionalObjects`、
  `ICoreWebView2ObjectCollectionView` slot3/4、`ICoreWebView2File` slot3 `get_Path`。
  绑定库只包到 v1 接口，这里按工程既有手法自镜像 vtbl + QueryInterface
  （同 `browser_panel_windows.go` 的 `wvRawVtbl` / `evtHandler`）。
- 挂载 / 反注册与 `ProcessFailed` 事件同一处：`desktop_windows.go` 每轮前端创建后
  `attachDropBridge(mainWebViewOf(w), …)`，收尾时 `detachDropBridge(wv)`。
- 老运行时没有 `AdditionalObjects`、非 Windows 宿主：只落日志，拖拽退回 multipart。

### 2. 前端（`web/app-chat.js`）

- `stageFiles()` 改为返回本批真正入列的附件（超限/超大的被跳过，保证与 File 对象
  一一对应不乱位）。
- 新增 `requestNativeDropPaths(files, added, view)`：仅当页面有
  `chrome.webview.postMessageWithAdditionalObjects` 时把这一批 File 交给宿主
  （带 `batch` 号供回话配对），失败静默保持 multipart。
- 新增 `JX.onNativeDrop(reply)`（= `applyNativeDropPaths`）：把这一批附件就地升级成
  「路径型」（`a.path = 真实路径`），发送时走既有 JSON `{path}` 通路登记原件路径。
- drop 处理器：`stageFiles` 之后调用 `requestNativeDropPaths`。拖拽观感、悬停高亮、
  页内 HTML5 拖拽（排队坞排序等）都不动。

### 3. 交付工具（`deliver.go`）

- `upload` 参数**改为可选**（schema 只 required `source`）。
- 新增 `resolveUploadFor(ref, sourceAbs)`：
  `uid` / 原件路径 / 工作区副本路径 → 显式引用优先；没给引用就按 `source`
  （工作区副本路径，大小写不敏感归一）反查同一条上传记录，取最新一条（同路径
  被重复登记时）。反查不到给可读错误：说明这类上传没有原件路径，并列出可用编号 +
  成品在工作区的位置，不猜目录去覆盖。
- `findUpload` 也认工作区副本路径（模型常把注记里的工作区路径原样当 `upload` 传回）。
- 登记回执与 `uploadpath.go` / `server.go` 的上传注记改成说清「交付会送回哪个位置」
  与「这次上传有没有原件路径」。

## 三、验证

已做（不碰浏览器、不影响运行中的实例）：

- `go build ./...`、`go vet .`、`gofmt -l` 全干净；`node --check web/app-chat.js` 通过。
- 临时针对性单测（跑完已删净）`TestResolveUploadFor` 9 例全绿：按 source 反查、
  大小写不敏感、uid、原件路径、工作区副本路径当 upload、工作区内原件、未登记文件
  报错文案、不存在的编号、同路径重复登记取最新。**其中第 2 例抓出真 bug**：
  反查最初写成 `canonicalFor == canonicalFor`（大小写敏感），文件不存在时
  `canonicalFor` 退回词法 Clean 就会漏判，已改用 `strings.EqualFold`。
- 机制真机实测（独立 WebView2 探针窗口，`.jxai/tmp/dropspike`，拖入真实文件）：
  宿主确实拿到 `CoreWebView2File.Path = D:\…\dropspike\main.go`。**这条 API 通路
  在本机运行时（155.0.4283.45）成立。**
