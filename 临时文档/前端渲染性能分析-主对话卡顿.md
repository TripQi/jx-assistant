# 前端渲染性能分析：为什么只有「数字经理」主对话卡

排查时间：2026-10-18 16:11 起（编程模式会话）
方法：只读源码调研（web/ 前端 + server.go 后端），结合上午《排查报告-20261018-闪退与主对话输入卡顿.md》
的实测数据（主对话 seq 1068、压缩后约 490 条消息常驻 DOM，其他会话几十条）。
本文档是那次报告第三节（输入卡顿）的全链路扩展：把「加载 → 渲染 → 流式 → 事件 → 输入」
五条路径的代码事实摆全，并给出分阶段修复方案（第一阶段随本文档落地）。

---

## 一、结论速览

| 问题 | 结论 |
|---|---|
| 前端是全量加载吗 | **是**。打开会话 `GET /api/sessions/{id}` 一次取全部消息，无分页无 limit；事件驱动的「就地翻新」也是整包重取 |
| 前端是全量渲染吗 | **DOM 全量常驻（无虚拟化、无 containment），渲染是「前缀复用 + 尾部重建」的准增量**。静态展示没问题；问题在几条与规模成正比（个别平方）的常驻路径上 |
| 为什么只有主对话卡 | 主对话在「规模 × 活跃度」两个维度都是全场最大：消息总量与用户气泡数最多（放大所有全列成本），且长期处于流式/事件轰炸状态（子对话回报、自动汇报轮、todo 广播）；其他会话消息少、跑完即停，同一套代码成本低几个数量级 |

一句话：**代码里每条路径的成本都 ∝ 当前会话的 DOM 规模或消息数，而数字经理对话把每个变量都推到了全场最大，还叠加了别人没有的「永远在跑」。**

## 二、代码事实（按链路）

### 1. 加载：全量整包

- `server.go:1642 handleGetSession` → `Store.MessagesWithSeq(m.ID)` 取**全部**消息；
  `trimMessagesForUI`（server.go:1621）只削审计工件正文与重复 prompt 快照，仍全量下发。
- `web/app-chat.js:262 loadSessionInto` 整包吃下 → `renderMessages(state.msgs, mainView, {jump:true})`。
- 事件驱动的整包重取（同一接口反复拉）：
  - 全局事件 `done / report_ready / stopped / session_updated / message` → `refreshCurrent()`
    （app-chat.js:2358、2412-2460）→ `openSession` → 整包 GET + 全量渲染；
  - attachRun 跟随后台执行时，轮内每条 `message` 事件 → `reloadMessages`（app-chat.js:4113-4120）
    → 整包 GET。
- **主对话特异性**：子对话 `sub_end`、回报 `report_ready`、todo 落库广播 `message`、
  权限审批 `session_updated`……全部以主对话为轴心。子对话一多，主对话空闲时也会被
  频繁整包重取（主对话几百条消息的 JSON 每次都是几 MB 级）。

### 2. 渲染：前缀复用 + 尾部重建，但 DOM 全量常驻

`renderMessages`（app-chat.js:2052）不是无脑 innerHTML 全刷：
- **前缀复用**：同会话、回合分界没变、分界前末条 seq 未变时，旧回合 DOM 复用
  （`st._pfxSid/_pfxLen/_pfxSeq/_pfxNodes`），只重建「最后一回合 + 插话 + 占位」的尾部。
- 但复用条件在新回合开始（用户发消息）、切换会话回来、编辑重发时全部失效 →
  整列 `box.innerHTML = ''` 全量重建 + 所有 markdown 重新 parse（app-chat.js:2110-2125）。
- 每次调用仍有全量 JS 遍历：`scanReported(msgs)`、resultOf 建表、`groupTurns` 全量分组。
- **无任何虚拟化**：style.css 全文零 `content-visibility`/`contain`。「折叠」只是
  `max-height` 视觉裁剪，DOM 节点一个不少——主对话 490+ 条消息（含全部表格/代码块/
  proc-row）常驻文档，任何布局失效都要在全量节点上重算。
- **尾部重建是「整回合」粒度**：轮内流每条 message 事件（工具结果/正文/env 行）→
  push → `renderMessages` → 最后一回合整体重建（app-chat.js:4136）。普通对话最后一回合
  只有几条消息，无感；主对话一轮汇报/派发可达几十上百条 → 单轮累积 O(回合大小²) 的
  DOM 重建 + markdown 重 parse。

### 3. 流式：全文重 parse + 全列测量

- `liveRender`（app-chat.js:2296）：每个 delta/reasoning 帧 → rAF →
  `el.querySelector('.md').innerHTML = md(view.state.streamText)` —— **累计全文**重新
  parse（自研逐行解析器，app-core.js:432 `md()`）+ innerHTML 重建，长输出 O(n²)。
- 消息列挂着 `MutationObserver(subtree:true)` + `ResizeObserver`（app-chat.js:1366-1377
  setupFolds）：上面任何 DOM 变化（流式每帧、尾部重建、fold 按钮增删）→ `scheduleFolds`
  → rAF → `applyFolds` → 对**全列每个用户气泡**逐个 `getBoundingClientRect +
  getComputedStyle + scrollHeight`（app-chat.js:1178-1310）——DOM 脏时首次读强制整页
  同步 layout。
- **主对话特异性**：用户气泡数全场最多（foldTargets 的选择器正是
  `.msg.user > .bubble, .msg.sysnote > .bubble`），且流式几乎常开。

### 4. 输入：每键强制同步布局（上午报告已定性，此处补机理细节）

- `autoGrow`（app-core.js:900）：`height:'auto'` → 读 `scrollHeight` → 写回 px。
  `.composer-input` 样式带 `min-height:72px; max-height:200px`（style.css:1483）——
  **1~3 行输入时高度根本不变**，即绝大多数按键的「两次样式写 + 一次强制同步读」
  纯属浪费；在几百条消息的文档上每次可达几十 ms。
- input 事件（app-chat.js:7118-7121 / app-right.js:436）同步执行 autoGrow +
  `persistMainDraftLS`（逐键写 localStorage）。
- `#input`/`#sub-input` 未关 spellcheck，中文场景白付逐键拼写检查。

### 5. 环境快照体积（次要放大器）

每条用户消息携带数 KB 环境快照文本（上午报告路径三已记录）：推高单条消息的
markdown parse 成本与整包 JSON 体积。属体积治理，非本轮主因。

## 三、「只有主对话卡」的机制对照表

| 主对话特点 | 放大哪条路径 |
|---|---|
| 消息总量全场最大（490+ vs 几十） | 每键 autoGrow 强制布局、新回合/切回时全量重建、scanReported/groupTurns 全量遍历 |
| 用户气泡全场最多 | applyFolds 每轮全列测量 ∝ 气泡数 |
| 长期 running（汇报轮/派发轮/接流） | liveRender 全文重 parse、尾部整回合重建、MutationObserver→applyFolds 常态触发 |
| 全局事件密度最高 | refreshCurrent/reloadMessages 频繁整包 GET + 全量渲染 |
| 单轮消息数巨大 | 尾部重建随每条落地反复执行，单轮 O(n²) |

其他对话：消息少（静态 DOM 小）+ 执行完即停（流式路径关闭）+ 不产生全局事件 →
同一套代码，成本小几个数量级，感觉不到。

## 四、修复方案

### 第一阶段（本轮落地，前端局部，不动消息架构）

1. **输入路径**：
   - `.composer-input` 加 `field-sizing: content`（WebView2 Chromium≥123 原生内容自适应），
     autoGrow 在支持的内核上退化为「清历史内联高度」的 no-op——量高路径彻底不跑；
   - 旧内核兜底保留原逻辑，但 input 事件里量高合并到 rAF；
   - 草稿落盘防抖 300ms（发送/切换会话/关页前同步 flush，见下）；输入框 `spellcheck=false`。
2. **离屏消息跳过布局**：`.msg` 加 `content-visibility: auto; contain-intrinsic-size: auto 200px`
   ——离屏消息跳过 layout/paint，等效低成本虚拟化；配合 applyFolds 增量化
   （已测气泡打标记跳过、只测新增，视口外的不测等滚入视口再补），否则逐气泡测量
   会把离屏内容强制实例化、吃掉收益。
3. **流式降载**：liveRender 对超长文本（>32KB）降频至 150ms；MutationObserver 回调
   里「变更全部落在 live 气泡内」时跳过折叠调度（那些变更本来就不在折叠目标里）。
4. **事件整包重取节流**：refreshCurrent 与 attached 模式的 reloadMessages 尾随防抖
   ~500ms 合并——子对话密集回报不再每条事件拉一次全量 JSON + 全量渲染。

### 第二阶段（建议后续单独立项）

- 后端消息分页（limit/offset 或 cursor）+ 前端向上翻页加载；
- 尾部重建改按 seq 增量 append（消掉 O(回合大小²)）；
- 环境快照不落历史正文、上下文装配时再展开（体积治理，渲染与 token 双收益）；
- 全局 SSE 加 Last-Event-ID 重放（顺带修上午报告第六节的断线丢事件族）。

### 预期效果

- 打字路径与消息总数解耦（field-sizing 后输入不再触发布局同步读）；
- 布局/绘制只发生在视口附近（content-visibility）；
- 流式 + 打字并发不再叠加（liveRender 降频 + 折叠调度收窄）；
- 主对话与短会话的输入手感拉平；WebView2 渲染进程「无响应→假重启」的触发面
  （上午报告第四节）同步缩小。

## 五、验证记录（2026-10-18 19:30，-webdir 开发模式 + 浏览器实测）

实测会话：3d6e0b2b9169e2eeb7（数字助理主对话，实测时 979→983 条消息、153 个用户气泡、约 12800 个 DOM 节点——比上午排查报告的 490 条又翻倍，佐证其增长与事件密度）。

| 验证项 | 结果 |
|---|---|
| field-sizing:content（主/子输入框 computed style） | 生效；CSS.supports=true → autoGrow no-op 路径激活；spellcheck=false |
| 打字路径（真实 input 事件循环 50 键计时） | **每键 0.01ms**（改前路径每键至少一次强制同步布局，同款读在干净 DOM 上即 0.7ms，流式脏 DOM 下更高——两个数量级以上改善） |
| content-visibility:auto（.msg / .tf-sec） | 生效：152 个用户气泡只测量视口内 21 个，离屏 131 个不进折叠体系等滚动补测 |
| 滚动补测（上翻 3000px 后） | foldDone 21→25：滚入视口的气泡 200ms 防抖后补测并入折叠体系 |
| 折叠交互 | 展开↔收起、按钮文案与 data-fold-open 状态正确 |
| 会话切换（回首页→重开，全量重建路径） | 正常：DOM 重建、cv:auto 与增量折叠照常工作 |
| 宽度变化（--content-w 860→700px） | ResizeObserver 宽度分支触发 resetFoldMarks 全量重测，折叠体系状态一致 |
