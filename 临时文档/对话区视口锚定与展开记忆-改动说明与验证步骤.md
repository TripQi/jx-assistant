# 对话区视口锚定与展开记忆 — 改动说明与验证步骤

时间：2026-10-30（编程模式会话）
提交：`efeafbdbbf`（只改 `web/app-chat.js`，+158/-11）
背景：对话区分块渲染（前缀复用 + 尾部重建）时视口定位跳来跳去——下面有更新
不断往下跳、上翻加载时不断往上跳，远程连接与手机端最明显。核心是渲染更新的
高度变化没有任何视口锚定补偿，加上钉住态被布局余波的钳位 scroll 误解除。

## 改了什么（五件，一条主线）

### 1. 视口锚定对 `anchorSave(view)` / `anchorRestore(view)`（followScroll 旁）
- 仅钉住阅读（`view._pinned`）时生效。锚 = `elementFromPoint` 命中视口**中线**
  的消息列直接子元素（跳过流式 live 气泡），变更前记元素 + 视口坐标 top，
  变更后按差值补 `scrollTop`——屏幕中间正在看的内容纹丝不动。
- 锚元素被尾部重建换掉时按 `data-key`（折叠段）/`data-seq`（消息行）找替身。
- 活动守卫：最近 250ms 内有触摸/滚轮（`view._actTs`，由 setupScrollTuck 的
  wheel/touch 监听记录）不补偿——程序写 scrollTop 会掐断手机惯性滚动。
- 接入点：`renderMessages`（重建前 save / followScroll 后 restore）、
  `applyFolds`（折叠应用前后，pinned 视图成对）。`liveRender` 不接：流式只动
  尾部，钉住时视口在中部不受影响，贴底跟随照旧。

### 2. 渲染钳位豁免窗口 120ms → 350ms（setupScrollTuck）
`_renderTs` 后的 synthetic 窗口覆盖折叠 rAF 与 200ms 补测余波。此前余波中的
钳位 scroll 被当成「用户滚回底部」→ 解除钉住 → 下一次跟随把视口拽到底——
正是「下面一有更新就往下跳」的主通路。

### 3. 思考/工具行展开记忆 `procOpenMem`（内存 Map，仿 foldOpenMem）
执行中每条 message 事件都整段重建尾部，行上挂的展开态随 DOM 换掉——点开一段
思考，下一批工具行到达就被折回。现在行键挂 `data-rk`（`kind:tool_call_id`，
无 tc.id 退回 `kind:seq`——同一消息多个调用靠 tool_call_id 区分），
`renderItem`（包装原 `renderRowItem`）渲染时查表恢复展开；用户点击写入
（`procOpenMark`），Ctrl+F 的 beforematch 程序性揭开不记。

### 4. 点击展开即钉住阅读 `pinViewForRead(el)`
过程行/折叠段（含继承段）/用户气泡折叠，点开的一律 `_pinned=true`：视口停在
展开处，新内容继续向下渲染但不再被跟随滚动拽走。收起不自动恢复跟随，滚回
底部或点「回到底部」由现有机制恢复。

### 5. 切换会话（jump 渲染）清三表记忆
`turnOpen`（折叠段）/`foldOpenMem`(用户气泡)/`procOpenMem`（过程行）在
`renderMessages` 的 jump 分支按会话前缀清掉，且提前重置 `_pinned`（旧会话的
钉住/锚不带进新渲染）。回来即默认折叠的「重新加载」态；刷新页面、手机端退出
重进内存表天然为空——同一约定，全程无 localStorage、无持久化。

## 明确没动
- 贴底跟随：`followScroll` 未钉住即贴底的路径原样（发消息/执行过程跟滚到底）。
- `content-visibility: auto` 性能优化保留；其占位突变对视口的影响由锚定兜住。
- 右栏子对话视图同套函数（view 参数化），未单独专项实测。

## 人工体验要点（远程/手机实测建议）
1. 手机远程访问，上翻停在中部等新消息到达：中间内容应不跳（此前上下窜）。
2. 执行过程中点开一段思考：应能从容看完（保持展开、页面不拽走）；滚回底部
   恢复跟随。
3. 切到别的会话再切回：之前展开的都应回到默认折叠。
