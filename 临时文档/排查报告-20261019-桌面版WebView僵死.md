### 关键证据

1. **挂起是进程级显式动作**：全部 22 线程 WaitReason=Suspended，只能来自 `NtSuspendProcess`/`SuspendThread` 一类外部调用（Chromium 页面冻结是调度器层的，线程不会呈 Suspended 态）。同树其他进程均为正常等待态——**只有渲染进程被单独挂起**。
2. **挂起时刻 = 13:10:55**：
   - desktop.log 中本地 UI（Chrome UA）最后一次请求 13:10:55（正在每 5–10s 轮询会话 3d6e0b2b 的 /progress，**轮询中途戛然而止**，非正常收尾）；
   - 此后 **11.5 小时零请求**（00:32:15 唯一一条 `GET /` 是 Reload 按下后浏览器侧发起的，见下）；
   - 渲染进程累计 CPU 仅 294.6s，与「13:06–13:10 活跃使用 ~4.5 分钟重度渲染 UI」吻合（本仓库前端本就有渲染重的问题，见《前端渲染性能分析-主对话卡顿.md》），活着的 UI 还要持续消化每 5 分钟的公司同步事件流，11.5 小时不可能只有这点 CPU；
   - System 事件 2004（虚拟内存耗尽）在 **13:03:16 / 13:04:04 / 13:05:23 / 13:09:52 / 13:10:56** 连响五次，最后一次点名 `python.exe (8140) consumed 38228369408 bytes`（≈35.6GiB）。
3. **不是崩溃**：13:06:19 之后**再没有任何新 msedgewebview2 进程被创建**（真崩溃退出必伴随渲染进程重建）；00:32:15 的 ProcessFailed 事件（kind=2）按官方枚举是 **RenderProcessUnresponsive（无响应）**，正是浏览器进程对「渲染进程不回 Ping」的判定——挂起 11.5 小时期间无输入所以从不触发，**用户 00:32 回来点击窗口才第一次触发**。
4. **挂起者无法从只读证据中指认**：本应用全部 Go 代码无任何挂起调用（沙箱只有子进程 spawn 时的 CREATE_SUSPENDED，随即恢复）；候选嫌疑：① WebView2 运行时在系统内存压力下的自保挂起（未再恢复，属运行时缺陷面）；② 系统侧内存优化器（机器上跑着 MSPCManager 电脑管家，其「内存优化/智能暂停」具备挂起后台进程的能力）。Windows 对 NtSuspendProcess 无审计日志，只读取证无法定谳——但无论谁挂的，**「挂起后无人恢复」是本次僵死的直接机理**，恢复责任应内建到应用自身（见修复方案）。
5. 窗口呈现形态吻合：宿主窗口不死（能拖动）、内容冻结（无合成帧）、光标处处文字选中（渲染进程不再处理 WM_SETCURSOR/鼠标移动，最后设置的 I 型光标永不更新）、点击无响应（输入事件堆在挂起的渲染管线里）。

## 三、「刷新界面」为什么无效（代码定位）

- `tray_windows.go:262 trayReloadUI()` → `trayApp.shellEval("location.reload()")`（即主 WebView 的 `ExecuteScript`）。**ExecuteScript 的执行者是渲染进程的 JS 主线程**——挂起/死循环/无响应三种状态下都永久排队，且该路径不触碰任何进程，因此「刷新」既救不了挂起也救不了崩溃循环。
- `desktop_windows.go:767-768` 常量错位：`pfRenderUnresponsive = 1 / pfRenderExited = 2`；[官方枚举](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/winrt/microsoft_web_webview2_core/corewebview2processfailedkind)实为 `0 Browser / 1 RenderProcessExited / 2 RenderProcessUnresponsive / 3 FrameRenderProcessExited / 4 Utility / 6 Gpu`。后果：
  - 真「无响应」走的是「渲染进程死亡：重新加载界面」→ `Reload()`（对无响应渲染进程无效，本案）；
  - 真「退出」走的是「容忍一次、5 分钟内第二次才刷新」→ 真崩溃后的第一次事件反而不恢复（好在 WebView2 对真退出会自动重建渲染进程并导航错误页，风险较低）。
- 应用侧已有的可靠恢复设施其实存在：`restartFrontendNow()`（BrowserProcessExited 与「10 分钟 3 次渲染死亡」分支在用）＝销毁控制器/WebView 并按 `frontendRestartReq` 走窗口循环热重启，能整体重建 WebView 进程树（挂起的渲染进程随之被浏览器进程拆掉）。**本案它从未被触发，因为 kind=2 被错映射进了「reload 即可」分支。**

## 四、修复方案（建议，本次未动代码）

1. **修枚举**：`pfRenderExited=1、pfRenderUnresponsive=2`（可顺带补 3=FrameRenderProcessExited、4=Utility、6=Gpu 仅记日志），`pfKindName` 同步。这是本次自愈链路失灵的直接原因。
2. **无响应升级为重建**：kind=2 连续触发（官方文档：无响应期间每几秒重复上报）≥2 次且窗口可见 → `restartFrontendNow()`，不再对无响应进程 `Reload()`（浏览器侧导航提交依赖渲染进程，注定卡死）。
3. **托盘「刷新界面」升级为真重启**：改为置 `frontendRestartReq`（热重启重建 WebView，窗口循环已支持原位重开）；菜单名改「重启界面」。或两段式：先 `ExecuteScript` 探测，3–5 秒无回包自动升级重建。重建成本≈一次窗口重开，前端状态本就在服务端。
4. **挂死自动检测（心跳）**：每 60s 对主 WebView `ExecuteScript('Date.now()')`（带完成回调，注意 COM 回调持引用防 GC，同 frontendPfHandler 纪律）；连续 2 次超时（如 10s）且窗口可见 → 自动重建 + 日志。一个探针同时覆盖「被外部挂起 / JS 死循环 / 渲染进程退出未重建」三类，误报面小（执行的就是最脆弱的那条线程）。
5. **根因面（另行立项）**：python/torch 任务把系统 commit 吃穿（38GB）引发整机雪崩（dwm/NTFS/Everything/前一实例/本渲染进程都是受害者）。建议沙箱 Job 对象加内存上限（sandbox_windows.go 已有 Job 基建，补 `JOB_OBJECT_LIMIT_PROCESS_MEMORY` 一类）或对 run_python/run_command 加资源护栏。
6. **本次现场恢复路径（供用户择时执行，AI 未代做）**：任务管理器结束 msedgewebview2 **PID 11312**（只杀渲染进程，后端/会话不受影响）→ WebView2 自动重建渲染进程并出错误页 → 托盘「刷新界面」随即生效（新渲染进程活着，location.reload 能跑）→ 界面恢复、状态对齐。比整体重启程序温和（当前后端还有会话在跑，含本次取证会话）。
