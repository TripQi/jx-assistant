# 【坚祥数字助理（GO版）】消息类型规范

> 本文是前后端之间的**消息类型契约**：一条消息在数据库里是什么类型、经 SSE
> 怎么发、前端用什么样式展示，全部在此定义。改展示只动前端，加类型只动后端
> ——两边都以本文为准，禁止在对方不知情的情况下私改类型语义。
>
> 适用版本：v0.9+（本文随类型演进同步修订；改类型必先改本文；
> 各项规则的**设计意图**集中在 §8，改动前先对齐意图再动规则）。

## 0. 三层模型

```
存储行（messages 表，kind 字段）          ← 单一源头，Go 常量在 kinds.go
   │  GET /api/sessions/{id} 返回全部行（含 kind/origin；正文按下发瘦身处理，见 §7）
   ▼
SSE 事件（Event.Type）                    ← 传输形态，message 事件带 kind/origin
   │  前端按 kind 分发（app-chat.js 的 ROW_ITEM_BUILDERS）
   ▼
展示条目（item kind）                     ← 显示形态，每类绑定一种标准样式
```

判定规则只有一条：**前端按 `kind`（必要时加 `origin` 子类）分发，永远不按
正文内容猜类型**——不解析 JSON、不匹配 `【…】` 前缀（仅旧库兼容，见 §5）。
后端保证每个可展示行落库时都带显式 kind。

## 1. 第一层：存储行类型（messages.kind）

### 1.1 对话内容（发给模型）

| kind | role | 含义 | 发给模型 | 前端展示 |
|---|---|---|---|---|
| `chat` | `user` | 用户真实发言（输入框/排队发出） | ✅ user 消息 | 用户气泡（右对齐，带复制/编辑重发） |
| `aiuser` | `user` | **AI 发出的用户消息**：数字助理派发的任务指令（dispatch_task/dispatch_sub/send_to_session）、【派发回报】、【待办任务派发】、【任务求助】。系统对待与用户消息完全一致——开新回合、组装时后面跟一条时间提示词（§1.2 time）、上下文/压缩/摘要按用户消息同权；区别只在：不可编辑重发、样式偏白。origin 沿用子类记法（task/dispatch/todo/help，见 §1.4） | ✅ user 消息 | AI 用户气泡：**左对齐、灰底（--chip）细边框**（`.msg.user.ai`，尾巴朝左下——微信灰底配白气泡，白页配灰气泡），下方悬停显隐时间/复制（靠左、无编辑）；长文折叠与用户气泡同一套 |
| `chat` | `assistant` | 模型输出（**复合行**，见 §3） | ✅ assistant 消息 | 拆成多个条目：思考折叠行 / 正文 / 工具行 |
| `chat` | `tool` | 工具执行结果（`tool_call_id` 配对） | ✅ tool 消息 | 并入对应工具行（展开看全文） |
| （compact 标记） | 任意 | 规则压缩的折叠标记（`messages.compact` 列，非空=已折叠：普通行存精简表示、工具结果/环境快照存 `omit`=整行不发）。与 kind 正交，不改行类型。**两级**：一级（首次折叠）正文保留、调用名+参数截断；二级（已折过的轮被更大的压缩范围再次覆盖时）只留用户输入与模型最终输出，中间过程全 omit | 模型看 compact 视图（思考/工具结果/环境快照省略）；组装时在「已折叠→原文」交界处注入 `foldBoundaryNote` 提示标签（user 消息，告知以上已压缩、细节可用 search_sessions/read_session_messages 查回；全折时缀尾）——文案为常量，前缀稳定 | **前端不受影响：原文照常完整展示**（所见≥所发）；groupTurns 按 compact 标记在连续折叠段的末尾（=压缩真实位置，可能在数轮之前）常显「已折叠 · 此前 N 个回合…」标注行（与发给模型的提示标签同位同义），多段折叠各自成行 |

### 1.2 上下文注入（发给模型的拼装材料；历史行不进上下文，组装时现场归位）

上下文注入是**一个概念类别、多个存储类型**：每种材料在请求里的位置和缓存
角色不同，所以分型存储；「上下文注入」指本组全部类型。

| kind | 含义 | 在请求里的位置 | 前端展示（变化驱动，见 §4） |
|---|---|---|---|
| `prompt` | 每轮拼装快照，正文为 JSON `{sys, env, tools}` | sys=第一条 system 消息；tools=请求体平级数组 | 首轮：系统提示词折叠行（用户消息上方）+ 运行环境/工具定义折叠行（紧随其后）；之后仅在变更时出「系统提示词变更 / 工具定义变更」折叠行 |
| `env` | 运行环境快照（权限/模式/能力/技能清单——**技能说明归这里**，随快照追加走，缓存友好）。**不含时间**：时间只随消息走（见下方 time 通道），环境快照因此只在真实环境变化时重发，用户发消息不再连带触发「环境更新」 | **追加式**：可见首条快照整份呈现；其后相邻快照按行差分渲染为短「环境更新」user 消息（变化行 + 不再适用清单），按落位进历史——已发送前缀绝不改写；摘要折叠后以边界后首条快照重新作为完整基线。**落库时机与发送时机分离**：「变化驱动」约束的是发给模型的差分重发（权限/能力/模式/工作区/技能等条目变了才发），不约束落库——落库由变更事件（PATCH 权限/计划/目标/工作区落库后、审批「始终允许」升级后**立即**落）与每次组装的例行检查（等值去重，两路不重复落行）共同驱动。**变更事件注记**：技能增减算出「（技能变更：…）」、权限/能力开关变更落「（权限变更：…）」——权限是环境条目，同一事实不重复记账，不另发 report 公告；注记行不参与快照等值比较，过期后在差分「不再适用」清单外静默消失 | 有变化才出「运行环境更新」折叠行（带行级 diff） |
| `summary` | 压缩摘要（origin=`auto`/`manual`，`covers_up_to` 记覆盖边界，`superseded` 记失效） | 注入在 system 之后、历史之前 | 「压缩摘要」折叠行（生成位置常显） |

#### time 通道（时间提示词；组装期派生，不落库）

每条用户侧对话消息——`chat`+user（真人发言）与 `aiuser`（AI 发出的）——后面
紧跟一条只含发送时刻的短 user 消息：`（发送时间：2006-01-02 15:04）`。
它在 `buildContext`/`contextStats` 组装时从该消息自身的落库时刻派生
（`context.go` 的 `App.timeAfter`），**没有存储行**：历史查询工具与前端消息流
都看不到噪音行；同一份存储重复组装逐字节相同，前缀缓存不受影响。时刻取消息
落库值而非挂钟——模型自己执行期间不产生新的时间消息，用户/AI 真发消息才跟
一条。历史库里的旧会话同样生效（派生依据是每行自带的 created_at）。
前端展示与运行环境同款：每条用户侧消息后面一条「时间提示」折叠行（展开即组装
原文，前端按同一规则从消息落库时刻派生）——一致原则（§4）：模型收到的上下文
前端都要能看到，可折叠但绝不缺失。

> 演进说明：2026-10 前时间是环境快照首行（「用户最近发消息时间」，取
> `Store.LastUserMessageAt`），用户每发一条消息就因这一行变化连带重发一条
> 「环境更新」。摘出独立通道后环境快照回到纯环境内容，时间随消息走。

### 1.3 系统注入与审计工件

| kind | role | 含义 | 发给模型 | 前端展示 |
|---|---|---|---|---|
| `report` | `user` | 系统注入的用户侧通知（中断/上传/回退/交付/续跑提示等，子类表见 §1.4） | ✅ user 消息 | 系统通知块（左侧虚线边框，常显，不可编辑重发） |
| `inherit` | `user` | 子对话继承标记，正文 JSON `{parent,count}` | ❌（组装跳过） | 继承段折叠条「来自主对话 · N 条」 |
| `request` | `system` | 最近一次发给模型的完整请求体（每会话只留最新一条） | ❌ | 不展示；「导出原始数据」的数据源 |
| `audit` | `system` | 运行事件审计（模型调用的用量与缓存命中/报错/停止/规则压缩/超限重试） | ❌ | 不展示；「导出日志」时间线的数据源 |

### 1.4 report / aiuser 的 origin 子类

report 与 aiuser 共用下面这张子类表：**aiuser** 是「AI 发出的用户消息」
（派发指令/回报/待办转交，见 §1.1），**report** 是系统侧通知（中断/上传等）。
2026-10 起 `task`/`dispatch`/`todo` 三类从 report 迁入 aiuser（对待向用户
消息看齐），report 仅剩系统通知。

| origin | 归属 kind | 内容 | 前缀（仅旧库兼容用，见 §5） |
|---|---|---|---|
| `dispatch` | aiuser | 【派发回报】子任务/子对话完成回报 | `【派发回报】` |
| `task` | aiuser | 【派发子对话】【数字助理派发】【数字助理转达】任务指令 | 同名前缀 |
| `todo` | aiuser | 【待办任务派发】定时任务转交 | `【待办任务派发｜` |
| `help` | aiuser | 【任务求助】任务会话找数字经理协调：问自己看不到的情况（别的会话在改哪些文件、现在合不合适动手）、要「同时只能一个人用」的资源排先后（requestmgr.go） | `【任务求助】` |
| `interrupt` | report | 【系统中断】【执行中断】 | `【系统中断】`、`【执行中断】` |
| `upload` | report | 【文件上传】（仅历史行；2026-10-19 起新注记不再独立落库，拼进用户消息开头的「用户附件：」块，见本表下方说明） | `【文件上传】` |
| `rollback` | report | 【文件回退】 | `【文件回退】` |
| `goal` | report | 【目标续跑】上限提示、`<goal_round>` 续跑指令 | `【目标续跑】`、`<goal_round>` |
| `tools` | report | 【工具目录变更】工具目录相对上一轮有增删时的尾部公告（能力开关不改编目，走 env 快照公告） | `【工具目录变更】` |
| `webview` | report | 【用户关闭浏览器】用户在右栏浏览器面板点 ✕ 关闭了页面（用户主动关闭，非崩溃；userstops.go）。【网页查看】的打开路径已不再注入（用户口径：打开什么是个人事），仅保留关闭通知 | `【网页查看】`、`【用户关闭浏览器】` |
| `stop` | report | 【用户停止程序】用户在进度面板停止了运行中的程序（后台作业优雅取消 / 子进程强制结束；userstops.go） | `【用户停止程序】` |
| `delivery` | report | 【交付结果】deliver_file 作业的执行结果注记（成功/失败同题；2026-11-02 前标题为【交付完成】，仅历史行） | `【交付结果】`、`【交付完成】` |

另：`chat` 的 tool 行里，会话被中断时系统给未执行/被中止调用补的合成结尾
（正文为「（会话被中断，…）」）带 `origin=interrupt`——属于结构必需的配对收尾
（每个 tool_call 必须有结果），前端照常按 `tool_call_id` 并入对应工具行。

**用户附件块（2026-10-19 起，upload 注记的新去处）**：文件上传接口不再落
独立 report 行，注记文本随响应返回，由发送链路拼进**用户消息正文开头**的
「用户附件：」块（`用户附件：\n<注记行逐字原样>\n\n` + 正文；`dispatch_task`
派发附件拼进任务消息开头，同形态）。注记随用户消息一起到达模型——插话/排队
场景不再出现注记先到、消息后到；uid/判重/顺延真实文件名/交付说明文案一字未改。
前端把附件块渲染成灰色附件行（截断 + title 全文），正文里的文件标记按
`fileClipName(块内《全名》)` 对号成胶囊。历史库中的独立 `upload` 行按本表原样
渲染，不做数据迁移。

## 2. 第二层：SSE 事件（Event.Type）

### 2.1 message（行级事件，与存储行同型）

`message` 事件推送一条刚落库的行：`message` 字段是行本体，`kind` 与存储
kind 一致（**一律显式携带**），report 行额外带 `origin`，assistant 行可带
`thinking` 原文与 `seq`。前端把它当作存储行同等分发。

### 2.2 流式增量（瞬态，不落库）

| Type | 含义 | 前端表现 |
|---|---|---|
| `delta` | 正文增量 | 输入区上方实时拼接 |
| `reasoning` | 思考增量 | 实时思考折叠块 |
| `tool_start` / `tool_end` | 工具开始/结束（end 带截断输出） | 工具行运行态 |
| `tool_wait` | 工具等待审批 | 提示条 |
| `resume` | 重连补发进行中的半句 | 补齐实时区 |

### 2.3 终态与控制

| Type | 含义 |
|---|---|
| `done` / `stopped` / `error` | 一轮执行结束：正常 / 用户停止 / 失败（error 进输入框上方报错条） |
| `retry` | 重试开始（人工点重试 / 网络失败自动重试）：本步已流出的半截作废、从头重新输出 |
| `auto_retry` | 自动重试提示：output 非空=提示条显示（第 X/5 次、几秒后重试），空载荷=重试成功、清除提示 |
| `pending` | 插话/排队队列变化 |
| `approval_required` / `approval_resolved` | 越权审批卡 |
| `question_required` / `question_resolved` | 模型提问卡（required 带 `deadlineMs`：ask 类限时提问的倒计时截止毫秒时间戳） |
| `question_deadline` | 提问卡停表广播（`held=true`）：用户悬停/触碰卡片或点停止按钮，倒计时转不限时，各端同步 |
| `ask_alert` | 提问久等声光提醒（设置·常规的询问提醒，默认 240 秒触发）：后端已响系统叮声；`output`=朗读文案，前端全屏闪烁并走语音组件 TTS 朗读，点击跳去作答；停表连提醒一并暂停 |
| `title` | 自动起标题 |
| `todos` | 待办清单变化 |
| `sub_start` / `sub_end` / `sub_tool` | 子任务执行进度（全局事件流） |
| `report_ready` | 派发回报就绪，父会话将续跑 |
| `run_start` / `session_updated` | 执行开始 / 会话元数据变化（刷侧栏） |

## 3. 第三层：展示条目类型与标准样式

assistant 是复合行，前端拆成以下条目（**拆分规则是契约的一部分**）：

| item kind | 来源 | 标准样式 |
|---|---|---|
| `user` | chat/user 行 | 右对齐气泡（主题色调浅蓝），悬停复制/编辑重发 |
| `time` | 组装期派生的时间提示词（跟随 chat-user / aiuser 行，前端同规则派生） | 折叠行「时间提示 · HH:MM」，展开即组装原文（与 envnote 同款） |
| `aiuser` | aiuser 行（AI 发出的用户消息：派发指令/回报/待办转交） | 左对齐灰底气泡（`.msg.user.ai`，--chip），**开新回合**——上一回合随之收口（最终输出带出复制/压缩等回合按钮）；下方悬停显隐时间/复制靠左、无编辑；长文折叠与用户气泡同一套 |
| `text` | assistant 正文 | Markdown 渲染气泡；回合**收尾答案**常显并挂操作按钮（= 最后一条正文且其所在行无伴随工具调用——打断回合停在半路的最后正文不算收尾，不带按钮、按过程折叠），长中间正文（显示宽度豁免：非空行 ≥3 或显示宽度 ≥100「字」，半角 3 个记 1 字）也常显但不带按钮 |
| `think` | assistant 的 `thinking` 字段 | 折叠行「思考 · N 字」 |
| `tool` | assistant 的 `tool_calls` + 配对的 tool 行 | 折叠行：工具名+运行态，展开看参数/结果 |
| `subtask` | `tool_calls` 中名为 `dispatch_task/dispatch_sub/send_to_session` 的调用 | 子任务卡（实时进度→完成态） |
| `plancard` | `tool_calls` 中名为 `exit_plan_mode` 的调用 | 计划卡（常显块）：标题 + 首段 +「点击查看全文」，整卡可点开右栏「计划」并定位到这一份 |
| `note` | report 行 | 系统通知块：左侧细边框虚线样式（`.msg.sysnote`）；**孤立单条与「尾部通知」常显**（尾部=最后回合里下方再无消息的最新一条——中断提示要一眼看到），其余与思考/工具/材料相邻则并入顶层大折叠（§4） |
| `summary` | summary 行 | 折叠行「压缩摘要 · 自动/手动 · 覆盖至第 N 条」 |
| `envnote` | env 行（有变化时） | 折叠行「运行环境更新」，展开行级 diff |
| `syshead` | prompt 行（首轮的 sys） | 折叠行「系统提示词已拼装」，用户消息上方 |
| `prompttail` | prompt 行（首轮的 env+tools） | 「运行环境」「工具定义」折叠行，紧随用户消息 |
| `syschange` / `toolschange` | prompt 行（后续轮次的变更） | 折叠行，标题即变更摘要 |

样式基元只有四种：**气泡**（对话内容）、**常显块**（note/最终正文）、
**折叠行**（proc-row：标题+展开）、**折叠卡**（回合过程段 tf-sec）。
新条目类型必须落进这四种之一，不发明新容器。

## 4. 前端展示政策：所见即所发 + 只讲变化

**一致原则（先于一切展示规则）**：模型能收到的上下文，前端都要能显示出来——
展开折叠后看到的内容与发给模型的逐字一致，只允许「折叠了多少行、按钮、排版」
这类纯展示差异；**绝不允许模型收到的上下文在用户界面缺失**，顺序也与模型
收到的一致。审计工件（request/audit）与继承标记不发给模型，因此不在对话区
展示（各有导出/折叠段的出口）。展示的顺序以模型侧的真实顺序为准：工具定义
（请求体顶层 tools，KV 前缀的开头）在最上，其后系统提示词（messages[0]）、
消息序列（每条用户侧消息后跟时间提示、运行环境快照在尾部）、模型输出。

每次请求都会完整重发系统提示词（协议如此）；「不变」= 与上次逐字节相同，
前缀缓存据此命中。因此上下文材料的展示政策是**只讲变化**：

- 首轮完整交代拼装顺序：工具定义 → 系统提示词（均在用户消息上方）→ 用户
  消息 → 时间提示（紧跟该消息）→ 模型输出，运行环境（首轮请求的最后一条
  user 消息）紧随其后；
- 之后每轮：内容不变就不出现任何卡片；
- 变化（系统提示词/工具定义变更、运行环境更新）才在发生位置补折叠行，
  标题给摘要、展开给行级 diff 与全文。
- **顶层大折叠全局统一**：回合内连续的可折叠项（思考/工具/子任务卡/上下文材料/
  系统通知）不分家，相邻就折进同一段，标签汇总各类计数（「N 次思考 · M 条上下文
  材料 · K 条系统通知」）；段内保留各自的行级小折叠（proc-row 展开原文）。锚点
  （常显）只有：回合收尾答案（最后一条正文且其行无伴随工具调用——打断回合的
  最后正文不算，不带按钮按过程折叠）、长正文（显示宽度豁免：半角 3 个记 1 字，
  ≥100「字」或 ≥3 非空行，英文多的段落不再按字符数虚高）、计划卡、孤立的系统通知，
  以及**尾部通知**——
  最后回合里下方再无任何消息的系统通知保持常显（系统中断提示往往是会话最后一
  条，重启后用户要靠它知道接着发「继续」，不能折没）。

此政策只属于前端展示层；存储行始终如实逐轮/逐变化落库。

## 5. 旧库兼容（只读判定，新代码禁用）

历史库里存在无显式类型的行，前端仅对**读取旧库**保留内容判定：
`chat`+user+`【派发回报】/【系统中断】/【执行中断】/【文件上传】/…前缀`
按 report 兼容（前缀清单见 §1.4）。新写入的行一律显式 kind+origin，
不得再新增靠前缀识别的类型。

## 6. 新增类型的流程（本契约的使用方式）

**后端三步：**
1. `kinds.go` 加常量 + 在本文 §1 登记含义（发给模型？什么位置？）；
2. 写入点用常量落库（report 类给 origin 子类并在 §1.4 登记）；
3. SSE `message` 事件带上 kind/origin。

**前端一步：**
4. `app-chat.js` 的 `ROW_ITEM_BUILDERS` 注册构造器，产出 §3 中的条目；
   需要新样式时先在 §3 登记样式基元。

禁止：前端按正文猜新类型；后端复用旧 kind 塞新语义；SSE 发不带 kind 的
可展示行。前后端任何一侧的改动如果触及本契约，先改本文再动代码。

## 7. 与现状的对照说明

- 技能说明（用户技能清单/正文）当前归**环境快照**（尾部、缓存友好），
  不是独立类型；若未来独立成料（如 `ctx-skill`），按 §6 流程新增。
- `request`/`audit` 是审计工件：不进上下文、不进子对话继承、不进分支复制，
  只服务「导出原始数据 / 导出日志」。
- 下发瘦身（server.go trimMessagesForUI）：`GET /api/sessions/{id}` 的面向前端
  展示的响应里，request/audit 的正文不下发（导出走 `/export` 服务端直读）；
  与上一条 sys+tools 逐字节相同的 prompt 快照只发空壳 `{}`（前端跳过空壳，
  只见变化行——§4「只讲变化」的对应瘦身）。存储行与导出内容不受影响。
- 存储层的 origin 字段同时服务 summary（auto/manual）、report 与 aiuser
  （§1.4），语义按 kind 区分，不冲突。
- time 通道（§1.2）没有存储行：组装期派生，导出原始数据里它就是请求体里
  的一条 user 消息，无需单独瘦身。
- **2026-10 第二批调整**：aiuser 气泡定稿为左对齐灰底（下沿悬停显隐时间/复制）；

- **2026-10 两项迁移**：①时间从环境快照摘出为独立 time 通道（组装期派生）；

  「用户气泡变体」灰底气泡，派发类独立成 aiuser 后撤销）。旧库行不迁移：

## 8. 设计意图速览（为什么是现在这样）

> 本节是设计决策的「为什么」索引：规则本体在 §1–§4，这里只记意图，
> 改动前先对齐意图再动规则。

1. **通道=投递语义，不是消息种类**。一条通道只约定「怎么进上下文、前端
   怎么显示」，不绑定内容形态——env 通道是「变化才差分注入」的环境类注入
   的总家（未来新的环境提示都可归这里）；时间因为更新更频繁（每条用户侧
   消息都跟一条）独立成 time 通道，两者前端渲染同一套折叠行。
2. **时间随消息走，不随环境走**。时间放进环境快照的代价：用户每发一条
   消息就因时间行变化连带重发一条「环境更新」。取消息自身落库时刻而非
   挂钟——模型执行期间不凭空产生时间消息；组装期派生不落库——历史查询
   工具与消息流零噪音行，所有写入路径（排队/插话/回报直写）天然覆盖。
3. **aiuser＝AI 说的「用户消息」**。派发指令/回报/待办转交本质是 AI 代替
   用户发起的对话轮：按用户消息同权对待（开回合、跟时间提示词、上一回合
   收口带出操作按钮），仅两点不同——不可编辑重发、样式左对齐灰底
   （微信灰底页配白气泡的倒置：白底页配灰气泡）。
4. **report 回归纯系统通知**。上传/中断/回退等注记用克制的虚线通知块，
   不扮对话气泡（曾为让派发通知像对话把整通道改成气泡样式，派发独立成
   aiuser 后回退初版）。
5. **尾部通知必须可见**。系统中断提示往往是会话最后一条，重启后用户靠
   它知道「发个继续」——最新一条消息（下方再无消息）的通知永不折叠。
6. **所见即所发**。模型收到的上下文前端必须可见（可折叠、绝不缺失），
   顺序与模型侧一致（工具定义是 KV 前缀的开头，所以排在系统提示词上方）。
   request/audit 不发给模型，因此不进对话区（导出是它们的出口）。
7. **折叠三层，顶层统一**。顶层大折叠：连续的可折叠项（思考/工具/材料/
   系统通知）不分家，一段汇总各类计数；段内行级小折叠（proc-row 展开原文）；
   气泡折叠：用户与 AI 消息同一套 6 行折叠，且**不分会话与视图**（主对话、
   工作任务会话、右栏子对话抽屉一致；超 6 行折、短消息不折、可展开收起）。
   锚点最少化——收尾答案（最后一条
   正文且其行无伴随工具调用，打断回合的最后正文不算——否则中断轮的短过程句
   会带一排按钮还不折叠）、长正文（按显示宽度：半角 3 个记 1 字，纯字符计数
   会让英文段落「看着短却被判长」）、计划卡、孤立通知、尾部通知，除此之外
   皆可折。
8. **操作行悬停显隐**。入口可发现性让位于界面整洁（常驻一排按钮让按钮与
   下一条消息的间距显得又短又乱）；行保留布局占位，平时化作留白、悬停即现，
   三类消息（用户/AI/助手）交互统一。
