# 调研报告：数字助理消息通道（aiuser）是否合并为「用户消息+标记」

> 调研时间：2026-10-20 00:00 ~ 00:40　项目：D:\智能体工作区\软著版数字助理
> 性质：只查不改。全部结论以源码 + 运行库（data/jx.db，只读）双重证据为准。

## 〇、结论速览

| 问题 | 结论 |
|---|---|
| 「分支把 aiuser 带走、用户消息不带」是否成立 | **不成立**。数据库实证：分支按 seq 前缀复制，chat 用户消息 8 条全带走、aiuser 恰在分支点之后未被复制——分支逻辑对两类消息一视同仁，无 bug |
| 用户看到的「分支里短暂出现转达消息」 | **前端竞态已定位到行**：后端 fork 先广播 `session_updated`（server.go:2634）→ 前端 `loadSessions` 进入 120ms 防抖（pending）→ `forkFromAnswer` 的 `await loadSessions()` 被**假 resolve**（app-core.js:716）→ `openSession` 找不到 brief、**乐观切换被跳过**（app-chat.js:152）→ 界面在整包 GET 返回前持续显示源会话（含转达、输入框仍绑定源会话——seq 788 发进源会话即此窗口内所为）。叠加次因：源/分支标题仅差「（分支）」且截断不可见、源会话执行中置顶，切回时也易点错 |
| aiuser 是不是「独立通道」 | 落库 kind 独立（aiuser），但**写入收口唯一**（deliverToSession/landUserSide）、**渲染层已是「用户气泡 + .ai 标记」**（同一个 userBubble 构造器 + 一个 CSS 类）。独立的部分只剩存储层的 kind 字段与各处 `kind==aiuser` 判定 |
| 推荐路线 | **C 分阶段**：①先修 A（forkFromAnswer 直接用 POST 返回的 meta 做乐观切换，+5 行根治，顺带修复所有「创建会话→切换」路径的同类竞态；A2 分支后缀可见）；②再做 B 架构合并（chat+origin 标记）——它消除「用户消息」判定的双清单、兑现原始设计意图、代码净减约百行，但它**不是**修 bug 的手段，是架构清理 |

## 一、bug 真相：数据层没有「带走 aiuser」

### 1.1 事件重演（数据/jx.db 实测）

源会话 `1906433702d1471d45`（「我记得我们特地做过让右侧面板根据不同对话…」）：

| seq | 时间 | 内容 | 说明 |
|---|---|---|---|
| …716→720 | 18:59 | 用户问浏览器预授权 → 模型收尾输出 | **第一段对话结束**（720 = 最后完成轮的收尾正文，行无伴随工具调用） |
| 721 | 23:40:07 | **aiuser**【数字助理转达】交付卡按钮手机端适配（origin=task） | 数字助理转达，注入即开新回合 |
| 722~787 | 23:40~23:46 | 新回合执行（改样式、双视口自查、提交） | 源会话持续 running |
| **788** | **23:47:52** | **用户消息：「你是分支出来的对话，你不要管那个数字助理转达…」** | **落进了源会话** |
| 792 | 23:48:34 | 模型回答浏览器问题 | |

分支会话 `cc74559d2312812a7a`（23:45:00 创建，fork 复制结果）：

- 共 388 行，seq 1..388，末条 388 = 源 720「不动代码，直接回答你的问题…」的副本；
- **aiuser 行数 = 0**；chat-user 行 8 条（= 源会话 seq≤720 的全部用户消息）。

handleFork（server.go:2549）的复制规则：`kind ∉ {summary,request,audit} 且 seq ≤ upTo` 一律复制；未指定 upTo 且会话在跑时截断到「最后一条带正文且无工具调用的助手行」（本例同样落到 720）。**两个条件都不区分 chat 与 aiuser**——不存在「分支边界只认用户消息」的代码。8 条用户消息全部被带走即为反证。

### 1.2 用户所见现象的成因（前端，已定位到具体代码）

**主因：`loadSessions` 防抖合并的「假 resolve」× `optimisticSwitch` 的 brief 缺失无兜底，乐观切换被静默跳过。**

完整时序（逐行对应代码）：

1. 用户点分支 → `forkFromAnswer`（app-chat.js:1063）`await api(POST /fork)`；
2. 后端 `handleFork` 在 `writeJSON` **之前** `broadcast(session_updated, fork.ID)`（server.go:2634-2635）——SSE 事件先于 POST 响应到达前端（本机 loopback 几乎必然）；
3. `handleGlobalEvent case 'session_updated'` → `loadSessions()`（app-core.js:713）：置 `loadSessionsPending=true`、开 120ms 防抖定时器，**此刻 GET 列表尚未发出**；
4. POST 响应到达 → `forkFromAnswer` 执行 `await loadSessions()` → 撞 pending → **`return Promise.resolve()` 立即假 resolve**（app-core.js:716）——此时 `state.sessions` 里还没有 fork；
5. `openSession(fork.id)`（app-chat.js:105）：
   - `const brief = state.sessions.find(s => s.id === fork.id)` → **undefined**；
   - `if (brief && …) optimisticSwitch(mainView, brief)` → **整段跳过**（app-chat.js:152）；
   - 后果：**壳不换、消息区不清空、`state.cur` 仍是源会话**——界面原样显示源会话的标题、消息流（含 721 转达 + 执行中的流式输出）与**输入框（绑定源会话）**；
   - 直到 `await loadSessionInto(fork.id, tok)` 的 GET 返回，才切换为分支真实数据（无转达）。

**窗口时长** = SSE→防抖 120ms + POST 响应 + loadSessionInto 整包 GET，本机约 0.3~1s、远程数秒。窗口内：

- 界面显示的是源会话的一切，但用户刚点完「分支」，心智上把眼前内容当作分支 →「**分支对话短暂显示了转达消息**」；
- 此刻发消息，发送目标 = `state.cur` = 源会话 → **seq 788「你是分支出来的对话…」落进源会话的直接解释——用户无需犯任何操作错误，只是点完分支立刻发了消息**；
- loadSessionInto 落地正确数据（或用户切换后重开）→ 转达消失 →「来回切换再回去看，分支里并没有」。

**触发条件与观感**：只要 fork 的 `session_updated` 先于 POST 响应到达即触发（本机几乎必现）；若 POST 偶然先到，`forkFromAnswer` 自己触发的 `loadSessions` 会正常等待，乐观切换照常执行。这解释了现象的**偶发性**（平时分支一切正常，恰逢源会话在跑、事件密集时才撞上）。

**次因（放大器）：源/分支在侧栏不可区分**——分支标题 = 源标题 +「（分支）」，列表截断后后缀不可见；且源会话执行中持续刷新 updated_at，**在侧栏排在分支之上**。用户「切走再切回」时也容易点回源会话，看到转达后强化「分支带走过转达」的印象。

> 其余排查过的路径均安全（列出以证穷尽）：`consumeStream` 有 `view.state.cur.id !== sid` 丢弃防护（app-chat.js:5301）；`attachRun`/`refreshIfDangling`/`endTurn` 均以当前 `state.cur` 为准并有多重复验；`handleGlobalEvent` 各分支均有 `viewing`/sessionId 过滤。**污染源不是 SSE 跨会话串写，而是乐观切换自身的跳过。**

> 修正记录：最初任务描述按「数据被带走」理解；经理插话后按用户实测修正为「短暂显示后消失」。库检验支持后者：**数据层从未把 aiuser 带进分支**。

### 1.3 对方案设计的影响

- 「方案 A = 分支逻辑排除 aiuser」**没有对应物可修**——分支逻辑本就不排除任何对话行，也不该排除（分支是 seq 快照，语义正确）。
- 真正该修的是**前端乐观切换被静默跳过**（§1.2 主因）与**分支会话辨识度**（次因），见 §4 A'。
- 通道合并（B）与本次现象无因果，只能作为架构决策独立评估。

## 三、方案对比

### A 最小修复（按新事实重写）：修「乐观切换被跳过」+ 分支辨识度

原设想的「分支逻辑把 aiuser 排除」无 bug 可修（§1.3）。按 §1.2 定位的代码级根因，最小修复分两层：

**A1（治本，修根因）——乐观切换不再依赖竞态中的列表刷新，三选一或组合：**

1. **`forkFromAnswer` 直接用 POST 返回的 meta**（最推荐）：fork 接口的响应就是完整 SessionMeta（同列表项同型），把它塞进 `state.sessions`（或直接传给 openSession 做乐观壳）后再 `openSession(fork.id)`——`brief` 必然命中，乐观切换必执行；`await loadSessions()` 可后置为不阻塞。改动集中在 forkFromAnswer 一处（app-chat.js:1063~1078），约 +5 行；左栏/右栏「分支对话」菜单（app-left.js:435 / app-right.js:348）同款改法。
2. **修 `loadSessions` 的假 resolve**（app-core.js:716）：pending 时返回**同一次在途的 Promise**（把 resolve 存起来供后到调用方共用），而不是 `Promise.resolve()`——语义修正为「等下一次真实刷新完成」。一行级改动，但影响所有 `await loadSessions()` 的调用方（收益面大、面也广，需过一遍调用点）。
3. **`openSession` 的 brief 缺失兜底**：找不到 brief 时也清空消息区进加载态（宁可为空，不可停留旧会话）。改动最小，但切换体验退化（壳短暂无标题），不如 1 优雅。

**A2（治标，防放大）——分支标识可见**：侧栏/顶栏让「（分支）」后缀不被截断吞掉（后缀保护或分支角标）；可选 toast「已切到分支，原会话保持不变」。

- 改动量：A1-1 约 +5~10 行（三个入口各改一处）；A2 约 10~30 行。
- 能否顺带消除同类问题：A1 修复的是**所有「新建会话后立即切换」路径的通病**（不止分支——凡「创建→loadSessions→openSession」的链路都可能撞同一竞态，如新建对话、派发子对话后的跳转），是普适修复；A2 消除「切回时点错行」。两者合起来，本次现象的三个观察（短暂显示、发错会话、回来后消失）全部闭环。

### B 架构合并：aiuser → chat + origin 标记

设计：kind=chat、role=user 不变，origin 承载子类（task/dispatch/todo/help——**这些值已经在用**）；前端按 `origin` 加 `.ai` 类与禁编辑。落库走 landUserSide 的「chat 带 origin」分支（该分支已存在，为插话 origin=interject 而设）——**「chat+origin 非空 = 非标准用户消息」是既成事实，合并进来自洽**。

- **后端注入点改造**：5 类写入方把 `kindAiUser` 改传 `kindChat`（每处 1 词）；landUserSide 的三分叉简化为两分叉；kinds.go 删常量。
- **前端渲染改造**：删 ROW_ITEM_BUILDERS.aiuser（chat 构造器 user 分支加 origin 判断决定样式类与编辑能力）；displayKindOf、foldVisible、lastTurnStart、pendingSteer 等 10 处 `kind==='aiuser'` 判定改为 `kind==='chat' && !!origin`（多数可径直删掉——chat+user 自动涵盖）；userBubble 判定同步；CSS 不动。
- **历史数据迁移**：`UPDATE messages SET kind='chat' WHERE kind='aiuser'`（origin 已带子类，无需补）——217 行，量级极小。可选「不迁移+前端保留 aiuser 读兼容」的双轨过渡（§5 旧库兼容已有先例）。
- **与其他逻辑的交互（风险清单，按 `Kind=="chat" && Role=="user"` 反查）**：
  - splitRounds / timeAfter / compactRound：判定**简化**（少一个并列条件），行为不变；
  - **handleEdit（编辑重发）**：按用户消息截断重发——合并后 aiuser 也会命中后端判定！须加 `origin==""` 守卫（前端编辑按钮同样）；
  - handleFork 的 IsRunning 截断、sessiontitle 自动起标题、usage/voice_used 统计、LastUserMessageAt：语义从「真人消息」扩为「含 AI 用户消息」——多数场景这**正是期望**（派发指令开头的子对话本就该用指令起标题），但需逐处过目确认；
  - 排队/插话（PendingMsg.Kind）、SSE message 事件、导出、搜索：透传或无特判，无影响；
  - 《消息类型规范.md》§1.1/§1.4/§3/§5 需按流程先改（契约文件先行）。
- **预计净增减**：后端约 −40 行、前端约 −70 行、迁移函数 +15 行——**净减约 100 行**，并永久消除「用户消息判定双清单」。
- **风险与回滚**：主要风险在「chat+user 判定点语义扩大」的审计遗漏（上表）；回滚 = git revert（代码）+ 反向 UPDATE（数据，kind 可由 origin 子类无损还原：`kind='aiuser' WHERE kind='chat' AND origin IN ('task','dispatch','todo','help')`）。

### C 分阶段：先 A 后 B

完全可行且推荐：两件事**零耦合**——A 是前端竞态修复，B 是存储/渲染架构清理。先 A 止血（乐观切换必执行、用户不再看错/发错），B 择机在「近期没有其他 AI 改这几处文件」的窗口做（涉及 agent/runtime/context/server 四个热点文件，与多 AI 并行开发有冲突面）。

## 四、推荐

**推荐 C：立即做 A（A1-1 为主 + A2 顺手），择机做 B。**

理由：

1. **本次现象的根因不在通道**——数据实证分支行为正确，症状来自前端乐观切换被 `loadSessions` 假 resolve 竞态静默跳过（§1.2 已定位到行），叠加源/分支辨识度低。A1-1（forkFromAnswer 直接用 POST 返回的 meta）+5 行即根治，且顺带修复所有「创建会话→切换」路径的同类竞态。
2. **B 值得做，但理由要摆正**：它兑现「数字助理消息=一种用户消息」的原始设计意图、消除双清单（防未来「只认 chat 漏 aiuser」式遗漏——这正是本次误报的想象空间来源）、净减百行；且客观条件极好——渲染层已就位、写入收口唯一、存量仅 217 行、origin 子类已在用。
3. **B 的成本如实**：不是删一个常量，而是「所有 `chat+user` 判定点」的一次语义审计（约 8~10 处），其中 handleEdit 必须加守卫；契约文件先行改。适合单独排一次提交，不宜与别的改动混做。

另附两条顺手项（可并入 A 提交）：
- 统一三处 aiuser 样式口径的注释（kinds.go / app-chat.js:815 / 规范文档均为「左对齐灰底」）；
- handleFork 的分支点截断逻辑保持现状——它对 chat/aiuser/report 一视同仁是正确语义，不建议动。
