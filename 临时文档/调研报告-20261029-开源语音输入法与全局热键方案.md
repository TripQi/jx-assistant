# 调研报告：开源语音输入法（本地模型 + 全局快捷键）与对接方案

调研日期：2026-10-29
目的：为坚祥数字助理配一套「全电脑任意位置、快捷键触发、本地模型识别」的语音输入能力。核心痛点：快捷键触发容易出一堆 bug，想直接拿开源成品改造对接，或借鉴其成熟思路。
源码已拉取：`.jxai/tmp/voice-ime-research/CapsWriter-Offline/`（浅克隆，master 分支）

---

## 一、结论（TL;DR）

1. **最贴合的成品是 [CapsWriter-Offline](https://github.com/HaujetZhao/CapsWriter-Offline)**：7k star、MIT 许可证、Windows 专用、纯本地离线（sherpa-onnx 加载 ONNX 模型，与本项目 `组件/voice/asr_worker.py` 同一技术栈）、按住 CapsLock/鼠标侧键说话松开即上屏。它的快捷键模块浓缩了全局热键所有防坑技巧，正是我们踩坑的地方，**强烈建议精读 `core/client/shortcut/` 目录（共 6 个文件，核心 226 行）**。
2. **模型替换极简单**：CapsWriter 服务端引擎是工厂模式（`EngineFactory._ASR_LOADERS`），每个引擎一个类（继承 `BaseASREngine`），Paraformer 引擎就是 `sherpa_onnx.OfflineRecognizer` 加载 ONNX——与我们的 xasr 模型加载方式完全一致。加自己的模型 = 新增一个 loader + 指向 `组件/voice/models/xasr/` 里的模型文件。
3. **两条落地路线**（详见第四节）：
   - 路线 A（拿来即用）：直接用 CapsWriter 客户端 + 改造服务端挂 xasr 引擎。1~2 天可用，但是 Python 双进程、独立托盘。
   - 路线 B（借鉴自研，推荐）：在坚祥 Go 里做输入法壳——`recorder_windows.go` 已有全套低级钩子 + winmm 录音代码，`asr_worker.py` 已有流式识别通道，只差把 CapsWriter 的「热键防坑 5 招」移植成 Go。单进程单交付，与现有组件体系（组件/voice）天然融合。
4. 关于「小米模型」：小米确实开源了 [MiMo-V2.5-ASR](https://github.com/XiaomiMiMo/MiMo-V2.5-ASR)（Apache-2.0），但它是 LLM 路线（MiMo-Audio-Tokenizer + LLM，需 CUDA ≥ 12.0），不是我们这种传统路线。没找到直接使用小米模型的开源输入法；不过这不影响——我们的模型已经在 sherpa-onnx 上跑通，CapsWriter 恰好就是 sherpa-onnx 生态，等价于「找到了用同类模型技术的输入法」。

## 三、CapsWriter-Offline 深度解剖（改造前必读）

### 3.1 架构：C/S 双进程，WebSocket 通信

```
┌─ 客户端 start_client.exe ────────────┐      ┌─ 服务端 start_server.exe ──────────┐
│ 快捷键监听(pynput LL钩子)              │      │ EngineFactory → ASR 引擎            │
│ 录音(sounddevice) → PCM 流 ──────────WS────→  │  ├ paraformer (sherpa-onnx ONNX)   │
│ 结果上屏(打字/粘贴) ←────文本+时间戳────WS──── │  ├ sensevoice (sherpa-onnx ONNX)   │
│ 托盘/浮条提示/热词/LLM润色(可选)         │      │  ├ fun_asr_nano / qwen3_asr (GGUF) │
└──────────────────────────────────────┘      │  └ + 标点模型 CT-Transformer        │
                                               └───────────────────────────────────┘
```
分离的理由（README 原文）：老电脑跑不动模型也能只跑客户端连局域网里别的机器；模型加载崩溃不影响热键监听。**这套职责划分值得照抄**：坚祥里 = Go 主进程（壳：热键/录音/上屏）+ asr_worker.py 子进程（模型），本来就是组件桥架构，完全对得上。

### 3.2 快捷键防坑 5 招（我们的痛点，全在 `core/client/shortcut/shortcut_manager.py`）

| # | 坑 | CapsWriter 解法 | 代码位置 |
|---|---|---|---|
| 1 | 全局监听 + 屏蔽原始按键 | pynput `keyboard.Listener(win32_event_filter=...)`：在 Windows 低级钩子回调里直接处理，命中快捷键且 `suppress=True` 时调 `listener.suppress_event()` 在钩子层吞掉按键（返回不透传），**不是事后撤销** | `create_keyboard_filter` / `create_mouse_filter` |
| 2 | 自己模拟的按键被自己的钩子抓到（死循环） | `ShortcutEmulator` 维护"正在模拟"标志，钩子回调先查 `_check_emulating()`，是自注入事件直接放行，KEYUP 时清标志 | `_check_emulating` |
| 3 | CapsLock 是切换键，长按吞掉后用户没法切大小写 | **短按（<0.3s）= 原功能，长按 = 说话**：短按结束时不识别，异步补发一次 CapsLock press+release（模拟切换），补发期间用 `_restoring_keys` 标志放行，避免补发事件再次触发自己 | `schedule_restore` / `_check_restoring` |
| 4 | 鼠标侧键 X2 长按吞掉后，浏览器"前进"失效 | 同上：短按取消录音后异步补发一次真实 X1/X2 点击（`emulate_mouse_click`） | `_handle_mouse_keyup` |
| 5 | 焦点应用差异（有的程序模拟打字丢字、有的输入法拦截） | 长按/单击双模式（`hold_mode`）+ 每键独立配置 `suppress`；配合按进程名单强制切换上屏方式（见 3.3） | `config_client.py: shortcuts` |

配套状态机：每个快捷键一个 `ShortcutTask`（`task.py`）：按下→录音开始；松开→时长 < threshold(0.3s) 判定为误触/短按（取消+补发），≥ threshold 判定为说话（送识别）。单击模式则是按一下开始、再按一下结束。
另有 `key_mapper.py`（VK 码↔键名映射表）、`event_handler.py`（keydown/keyup 分发）、线程池 4 worker（钩子回调绝不做慢活——回调里只置状态，录音/识别在别处，防钩子超时被系统摘除）。

**这 5 招对应的 Go 实现难度**：第 1 招 = `SetWindowsHookEx WH_KEYBOARD_LL/WH_MOUSE_LL` 回调里对目标键返回 1 不调 `CallNextHookEx`（`recorder_windows.go` 已有整套钩子代码）；第 2 招 = 过滤 `LLKHF_INJECTED` 标志（`recorder_windows.go` 注释里已实现"自家 computer_* 注入的事件带 LLMHF_INJECTED 标记，刻意过滤"——**同一招，现成的**）；第 3/4 招 = `SendInput` 补发 + 超时窗口内放行该键；第 5 招 = 配置结构照抄。→ **Go 侧没有未知难点，全是已掌握的技术重新组装**。

### 3.3 文字上屏：双模式 + 剪贴板恢复（`core/client/output/text_output.py`）

- **模拟打字**（默认）：`keyboard.write(text)`——逐键注入虚拟键码/Unicode 事件，绕过中文输入法（不会打进输入法候选框），适合大多数应用。
- **剪贴板粘贴**：存原剪贴板 → `pyclip.copy(文本)` → pynput 模拟 Ctrl+V → 0.1s 后恢复原剪贴板。配 `paste_apps = ['WeiXin.exe', 'Telegram.exe']`：**按前台窗口进程名单强制粘贴**（微信等模拟打字会丢字/表情乱码的应用）。`core/tools/window_detector.py` 负责取前台窗口进程名。
- 细节：`trash_punc` 去末尾标点（短句去、长句留，且按应用名单强制去）——输入法场景"说话上屏不该带句号"的产品化细节，值得借鉴。

### 3.4 模型替换扩展点（服务端）

- `core/server/engines/factory.py`：`_ASR_LOADERS = {'sensevoice':…, 'paraformer':…, …}`，`create_asr_engine(model_type)` 按名实例化。**新增自有模型 = 加一个 loader + 一个 Engine 类**（实现 `BaseASREngine` 接口：创建流、喂 PCM、出 token/时间戳）。
- `core/server/engines/paraformer_onnx/asr_engine.py`：引擎内核就是 `sherpa_onnx.OfflineRecognizer(model=…, tokens=…)`——与 `组件/voice/asr_worker.py` 加载 xasr 的方式同族。CapsWriter 甚至内置了各模型的下载/导出 notebook（`models/Paraformer.ipynb` 等），可照葫芦画瓢做 xasr 的导出脚本。
- 性能参考（README，20s 音频）：Paraformer CPU 0.6s / SenseVoice GPU 0.15s——按住说话场景延迟可控；我们 asr_worker 已有流式协议（`stream_start/chunk/end`，partial 增量），对接后还能做到边说边出灰字。

### 3.5 其他值得借鉴的工程设计

- **热词系统**：`hot.txt` 音素模糊匹配强制替换（专有名词纠错）+ `hot-rule.txt` 正则替换——工厂场景术语（料号、工序名）刚需。
- **数字 ITN**：「十五六个」→「15~16个」，全离线规则引擎（`core/tools/chinese_itn/`）。
- **LLM 角色**：识别结果开头命中角色名→交给 LLM 润色/翻译后再上屏（坚祥本身就是 LLM 助手，天然可做）。
- **对讲机/单击双模式、UDP 局域网控制、日记归档、录音留档**（保密审计友好）。

## 四、落地路线（二选一或先 A 后 B）

### 路线 A：直接拿 CapsWriter 用（1~2 天出活）

1. 服务端：`EngineFactory` 注册 `xasr` 引擎——包一层，内部走 `组件/voice/asr_worker.py` 同款 sherpa-onnx 加载（或干脆把 asr_worker 协议适配进引擎类，模型文件复用 `组件/voice/models/xasr/`）。
2. 客户端：不改或微调（默认 CapsLock 说话已经很顺手）。
3. 坚祥主程序与二者并存即可，互相不打扰；后续想统一 UI 再迁移。
- 优点：立即可用、免费升级上游（社区在持续修 bug）、交付压力最小。
- 缺点：Python 双进程常驻（内存 ~几百 MB 起步）、双托盘图标、与坚祥的组件/配置体系割裂；MIT 许可证允许闭源改造无法律问题（保留版权声明即可）。

### 路线 B：借鉴自研进坚祥（推荐，1~2 周量级）

坚祥已有底子比想象中厚：
| 需求模块 | 坚祥现状 | 缺口 |
|---|---|---|
| 全局键鼠钩子 | `recorder_windows.go`：WH_KEYBOARD_LL/WH_MOUSE_LL 纯 syscall 实现，含 INJECTED 过滤、回调不阻塞纪律 | 增加"目标键按下/松开状态机 + 吞键（返回1）+ 短按补发 SendInput"（3.2 的 5 招） |
| 麦克风采集 | `recorder_windows.go`：winmm waveIn 16kHz/mono/16bit 现成 | 无（直接复用） |
| 本地 ASR | `组件/voice/asr_worker.py`：sherpa-onnx + xasr，transcribe 与流式协议齐备，组件桥常驻 | 无（直接复用） |
| 上屏 | 无 | `SendInput` 模拟打字（Unicode KEYEVENTF）+ 剪贴板+Ctrl+V 双模式 + 前台进程名单（GetForegroundWindow→进程名，`tool_computer_windows.go` 应有同款 API） |
| 应用内热键 UI | `web/app-hotkeys.js` 已有快捷键配置控件，语音组件已在用 | 把系统级热键配置接进同一 UI |
- 优点：单 exe 交付（模型组件已随组件体系分发）、UI/托盘统一、热词和 LLM 润色直接挂坚祥现有能力、无 Python 客户端常驻。
- 风险：快捷键边角 bug 要自己趟（所以先读透 CapsWriter 那 226 行 + 它的 issues）；建议上线前按 3.2 的清单逐条压测。

### 建议节奏

先跑通路线 A 验证体验（热键手感、识别准确率、目标应用兼容性），团队用两周攒真实使用反馈 → 再按路线 B 把壳重写进 Go（此时 CapsWriter 客户端当"参考答案"逐条对照）。避免直接自研时凭空猜坑。

## 五、已知坑清单（压测项）

1. **管理员权限窗口**：钩子/注入对提权窗口无效 → 坚祥需以管理员运行或manifest 申请 UIAccess（CapsWriter FAQ 同样要求"想在管理员程序中输入需以管理员运行客户端"）。
2. **UAC 安全桌面、全屏独占游戏**：低级钩子收不到或注入无效——所有同类产品都无解，文档里写明局限即可。
3. **模拟打字 vs 粘贴**：微信/Telegram 等模拟打字丢字 → 进程名单强制粘贴（CapsWriter 默认名单可直接抄）。
4. **剪贴板污染**：粘贴模式会短暂覆盖剪贴板（CapsWriter 0.1s 后恢复）；剪贴板历史工具（Win+V）里会留痕，保密场景需开关。
5. **钩子超时被摘**：回调里绝不做慢活（我们 recorder_windows.go 已有此纪律，保持）。
6. **中文输入法冲突**：模拟打字必须绕开输入法（直接 Unicode 注入），否则文字被输入法吃掉——CapsWriter 用 keyboard.write 而非 pynput.type 正是此因（text_output.py 注释原文）。
7. **识别期间焦点被用户点走**：结果注入到"当前"前台窗口。低延迟（<1s）+ 松开即送可大幅缓解；极端场景接受现状。
